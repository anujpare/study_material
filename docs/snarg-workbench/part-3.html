III · Commitments and Fiat–Shamir · Lecture §4

Now we have to get rid of the imaginary box

The Fibonacci verifier worked only because we pretended there was a trustworthy box holding the polynomials. Without that box, a cheater could wait to hear the random point, then invent answers that agree there. So the first missing step is to fix the polynomials before the question arrives.

We've solved this kind of problem once before. A Merkle root fixed an encoded PCP string and authenticated a few bit positions. Now we need the same idea for our polynomial oracle: fix the polynomial, then authenticate its value at a randomly chosen field point.

A polynomial commitment lets the prover make a short commitment \(c\) to a polynomial \(f(X)\). Later the verifier chooses a point \(z\), and the prover supplies a value \(y=f(z)\) together with a short opening proof. The verifier checks the opening against the original commitment, without receiving all the coefficients of \(f\).

The lecture describes four algorithms. We'll go through what each is for, rather than treating the list as something to memorize.

AlgorithmMeaning
Setup\(\operatorname{Setup}(d,\lambda)\to pp\). Choose public parameters \(pp\) that support polynomials of degree at most \(d\), at security level \(\lambda\).
Commit\(\operatorname{Commit}(pp,f)\to c\). Fix the polynomial and produce its short commitment \(c\).
Open\(\operatorname{Open}(pp,f,z)\to\pi\). Produce a proof \(\pi\) for the evaluation \(y=f(z)\).
Verify\(\operatorname{Verify}(pp,c,z,y,\pi)\to\{0,1\}\). Check the claimed evaluation against the commitment.

The first two algorithms prepare and fix the polynomial. The last two answer and verify a later question about its value. That's how we replace the polynomial oracle.

What stops the prover from lying?

There are two required properties.

Correctness

If the prover commits to \(f\), then honestly opens the true value \(f(z)\), verification must accept. This is what makes the scheme usable at all.

Evaluation binding

Suppose a cheater makes one commitment \(c\) and then claims two different values \(y\ne y'\) at the same point \(z\), with proofs that both verify:

\[ \operatorname{Verify}(pp,c,z,y,\pi) =\operatorname{Verify}(pp,c,z,y',\pi')=1. \]

The scheme must make this computationally infeasible. Formally, every polynomial-time adversary has at most negligible probability of doing it. A probability is negligible in \(\lambda\) if it eventually becomes smaller than \(1/p(\lambda)\) for every fixed positive polynomial \(p\).

These properties give us honest openings that work and prohibit conflicting openings at a chosen point. That's the behavior the ideal verifier expected from its polynomial oracle. \(\square\)

For the complete SNARG construction, the commitment implementation must also enforce the permitted polynomial degree and consistent evaluations across different queried points. The interface in the notes does not spell out a concrete construction or its full security proof.

One warning: a polynomial commitment need not hide the polynomial. Binding is not the same as zero knowledge, which is a separate privacy property.

Before removing a challenge, see what it does

Our goal is still a non-interactive proof of a computation. But before replacing the verifier's random question in a complicated polynomial protocol, let's do it in a simpler one with the same message order. Schnorr's protocol gives us a first message, an unpredictable challenge, and a response we can check by one equation.

The question in Schnorr is whether someone knows a secret exponent \(x\) for a public value \(h=g^x\). This is a different application, but the way the verifier challenges the prover is exactly what we need to understand before applying Fiat–Shamir to our polynomial proof.

We use a cyclic group \(G\) of prime order \(q\), generated by an element \(g\). Think of the group operation as multiplication. Every group element is some power of \(g\), and \(g^q=1_G\), the group identity. Exponents are calculated modulo \(q\).

The public value is \(h=g^x\). The prover knows \(x\); the verifier knows only \(h,g,q\). In Schnorr's protocol, they exchange three messages:

Prover \(P\)
⟶
Verifier \(V\)
Pick random \(r\); send \(u=g^r\)
⟶
Receives \(u\)
Must answer an unknown question
⟵
Pick random \(c\in\mathbb Z_q\)
Send \(z=r+cx\pmod q\)
⟶
Check \(g^z=u h^c\)

Why all these new letters? The prover picks \(r\) to hide the secret in a fresh random value \(u\). The verifier then picks \(c\), after receiving \(u\), so the prover cannot choose \(u\) knowing which challenge it must answer. The response \(z\) combines \(r\) with the secret \(x\) in a way the verifier can check using only public \(h\).

Check a real Schnorr equation

Use the order-11 subgroup generated by 2 modulo 23. The secret is \(x=3\), so \(h=8\). Move \(r\) or \(c\) and see the same equation hold.

HW2 · Problem 3(a–c)

Prove completeness, privacy, and knowledge extraction

The homework asks three different questions. First, why does an honest prover always pass? Second, could an honest-verifier transcript be generated without knowing the secret? Third, why does answering two different challenges to the same first message reveal the secret?

Show the three worked proofs

(a) Completeness

An honest prover sends \(z=r+cx\). Substitute it into the verifier's equation:

\[ g^z=g^{r+cx}=g^r(g^x)^c=u h^c. \]

The second equality uses \(g^{a+b}=g^ag^b\). The last equality substitutes \(u=g^r\) and \(h=g^x\).

Both sides are equal for every choice of \(r,c\). That proves perfect completeness. \(\square\)

(b) Honest-verifier zero knowledge

We want to produce a transcript \((u,c,z)\) that looks exactly like an honest exchange, but without knowing \(x\). Work backwards from the verifier's equation. Pick \(c\) and \(z\) uniformly at random, and define

\[u=g^z h^{-c}.\]

Then \(g^z=u h^c\), so the transcript passes the check. But does it have the right distribution? In the real protocol \(r\) and \(c\) are independent and uniform, and \(z=r+cx\). For each fixed \(c\), adding the fixed number \(cx\) to uniform \(r\) merely rearranges the field elements, so \(z\) is uniform. Once \(c,z\) are chosen, the equation determines exactly the value \(u=g^z h^{-c}\).

Thus the simulated \((u,c,z)\) is distributed exactly like a real honest-verifier transcript. The simulator never used \(x\). That establishes honest-verifier zero knowledge. \(\square\)

(c) Extracting the witness

Imagine a prover sends the same \(u\), then successfully answers two different verifier challenges \(c\ne c'\) with responses \(z,z'\). We have

\[g^z=u h^c,\qquad g^{z'}=u h^{c'}.\]

Divide the two equations. The same \(u\) appears on both sides and cancels:

\[ g^{z-z'}=h^{c-c'}=g^{x(c-c')}. \]

Because \(g\) has order \(q\), the exponents are equal modulo \(q\). And because \(q\) is prime and \(c\ne c'\), the difference \(c-c'\) has an inverse. We can solve for the secret:

\[\boxed{x=(z-z')(c-c')^{-1}\pmod q.}\]

An extractor can try this by running the prover twice from the same state after it sends \(u\), giving it a different challenge the second time. This is called rewinding. Two independent challenges coincide with probability \(1/q\); in that case the division is impossible for that pair.

Two valid answers to different challenges force a recoverable witness. This is the special-soundness property we'll need when counting cheating challenges. \(\square\)

Why does message order matter?

Suppose one proof has a cheating probability of \(1/2\). Repeating it several times should reduce that probability. But doing the repetitions one after another is not the same protocol as doing them all at once.

A three-message Sigma protocol has the order \(u\to c\to z\): the prover commits to its first message, the verifier chooses a challenge, and the prover answers.

Sequential repetition

\(u_1\to c_1\to z_1\)
\(u_2\to c_2\to z_2\)
\(\cdots\)

The first conversation finishes before the next first message is sent.

Parallel repetition

\((u_1,\ldots,u_t)\)
\(\downarrow\)
\((c_1,\ldots,c_t)\)
\(\downarrow\)
\((z_1,\ldots,z_t)\)

All first messages must be sent before any challenge is revealed.

Both forms can reduce soundness error. The subtle difference appears when we try to simulate the conversation without a secret witness.

HW2 · Problem 2(a–c)

Zero-knowledge under sequential and parallel composition

The Hamiltonian-cycle proof from the lecture has perfect completeness and soundness error \(1/2\). The verifier accepts the repeated protocol only if all \(t\) copies pass. (a) Show sequential repetition remains zero-knowledge. (b) Explain why the standard simulation argument does not establish zero-knowledge for parallel repetition against a malicious verifier. (c) Show that parallel repetition remains honest-verifier zero-knowledge.

Work through the difference in the simulators

(a) Sequential repetition

The simulator deals with the first session before the second starts. It simulates that session against the verifier in its current state, then continues to the next session and uses the same simulation method again. A malicious verifier might remember the earlier messages, so we must respect its state; we cannot simply say that its sessions are independent.

Each replacement of a real session by a simulated one is indistinguishable under the original zero-knowledge guarantee. Replacing a polynomial number of sessions one at a time preserves indistinguishability by a hybrid argument: if the first and last transcript distributions were distinguishable, some neighboring replacement would also have to be distinguishable.

The simulator can finish and justify each session before the next begins. That is why the ordinary sequential composition proof works. \(\square\)

(b) Parallel repetition

In the Hamiltonian-cycle simulator, the simulator prepares a first message tailored to one of two possible challenges. It ordinarily hopes to guess the verifier's challenge, then rewinds if it guessed wrong.

With \(t\) parallel repetitions, the simulator must send all \(t\) first messages before seeing the challenge vector. To prepare them using the same trick it must guess all \(t\) challenge bits. If the verifier chooses independent bits, one particular guess succeeds with probability \(2^{-t}\), requiring an expected \(2^t\) guesses. With malicious verifiers, challenges can also depend on the complete vector of first messages.

So the usual efficient sequential simulator no longer works. This does not prove that every parallel protocol fails zero-knowledge; it shows precisely why this simulation proof cannot establish it. \(\square\)

(c) Parallel honest-verifier zero knowledge

An honest verifier chooses the \(t\) challenges independently and uniformly, without depending on the first messages. We can simply run the original honest-verifier simulator \(t\) independent times and place all the simulated first messages, challenges, and responses in the three batches.

Each simulated copy has the correct honest-verifier distribution, and the copies are independent in both the real and simulated experiments. Thus the complete batched transcript has the same distribution as a real honest execution.

The parallel protocol remains honest-verifier zero-knowledge. The distinction is about which verifier we are trying to simulate and when its challenges become known. \(\square\)

For Fiat–Shamir, we will want the parallel three-message form: one batch of first messages, one batch of challenges, one batch of answers. The challenge batch can then be derived from a hash.

How can we remove the verifier's message?

We have now seen the same three-message pattern twice. In Schnorr, the verifier asks for a random group challenge; in our polynomial proof, it asks for a random evaluation point. Both questions must arrive only after

Look at the order of messages. First the prover fixes a first message \(u\). Then the verifier chooses a random challenge \(c\). The prover uses \(c\) to calculate a response \(z\).

Suppose both sides have access to a hash function \(H\) modeled as a random oracle. It returns a random-looking, consistently stored answer for each new input. Instead of waiting for a verifier, the prover can set

\[c=H(\operatorname{Encode}(x,u)),\]

where \(x\) is the public statement and \(\operatorname{Encode}\) unambiguously combines \(x\) and \(u\) (and, in practice, the protocol's public parameters). The output must be mapped into the original challenge space.

After calculating \(c\), the prover calculates \(z\) exactly as in the interactive protocol. It publishes \(\pi=(u,z)\). The verifier, who knows \(x\) and receives \(u,z\), computes the same \(c\) and performs the old verification test.

What has changed, and what has not?

The verifier no longer needs to send anything. That's the Fiat–Shamir transformation. The original check still works for an honest prover, since both sides calculate the same challenge.

But the hash has not made an insecure protocol magically secure. If the original challenge has just one bit, a cheater who can answer one of the two choices still has a good chance of succeeding. We need a large enough challenge space, or repeated tests, before applying the transformation.

Why honest verification still succeeds

The honest prover fixes \(u\), derives \(c\), and calculates the same response \(z\) it would have calculated after receiving \(c\) from a verifier. The new verifier reconstructs that exact \(c\) from \(x,u\). It therefore checks the same equation as the old verifier.

Thus the algebraic completeness argument carries over. Soundness against cheating, however, needs its own random-oracle argument; it does not follow merely from changing who calculates \(c\). \(\square\)

This is the missing non-interactive step in both constructions. For our earlier PCP/Merkle argument, the hash can determine the random bit positions. For a polynomial IOP, it can determine the random evaluation challenges after the polynomial commitments are fixed. The exact security proof depends on the protocol and the random-oracle model; simply hashing a challenge is not by itself enough.

HW3 · Problem 2(c)

A bound for a particular cheating strategy

Suppose a cheater fixes \(z,u\) before asking for \(H(h,u)\). Assume \(h\ne1_G\). Explain why at most one of the \(q\) challenges can make that fixed pair pass, and why \(Q\) tested pairs succeed with probability at most \(Q/q\).

Count the successful challenges

The verifier's equation is \(g^z=u h^c\). Rearrange it:

\[h^c=g^zu^{-1}.\]

Once the cheater has fixed \(u,z\), the right side is one fixed group element. Because the group has prime order and \(h\ne1_G\), \(h\) generates the group: the powers \(h^0,h^1,\ldots,h^{q-1}\) are all different. Thus at most one value of \(c\) can satisfy the equation.

For a fresh random-oracle input, \(c\) is uniform among \(q\) choices. So one fixed attempt succeeds with probability at most \(1/q\). For \(Q\) attempts, the probability of success in any attempt is at most the sum of the individual probabilities, by the union bound:

\[\boxed{\Pr[\text{a tested candidate passes}]\le Q/q.}\]

Querying the same input repeatedly does not give new random challenges, and an additional unqueried final attempt would have to be counted separately.

The bound comes from one acceptable challenge per fixed pair, not from a vague claim that the hash is hard to guess. This proves the bound for the specified attack, not full security against every possible prover. \(\square\)

Can one verifier pass a non-interactive zero-knowledge proof on to another? Why is a recording of an interactive zero-knowledge conversation different?

Show the distinction

Anyone who has a publicly verifiable non-interactive proof \(\pi\), its statement and the public setup can run the verification algorithm. The proof can therefore be passed on.

But a recording of an interactive zero-knowledge conversation doesn't by itself prove that the real prover took part. The zero-knowledge property gives a simulator that can create a convincing-looking verifier view without knowing the witness. A publicly verifiable proof is transferable; a simulatable interactive transcript is not the same sort of evidence. This doesn't rule out a real-time relay attack. \(\square\)

Homework: don't claim more than you've proved

In cryptography, words like “sound,” “knowledge,” and “zero knowledge” describe different guarantees. These questions test whether we can tell them apart.

HW3 · Problem 1(a)

Can knowledge error be smaller than soundness error?

Suppose some prover makes a false statement pass with probability greater than \(1/3\). Could the protocol have knowledge error less than \(1/3\)?

Show the contradiction

No. A proof-of-knowledge property with knowledge error \(\kappa\) demands that a prover succeeding with probability greater than \(\kappa\) allow an efficient extractor to recover a valid witness. If \(\kappa<1/3\), the false-statement prover from the question would exceed that threshold. The extractor would have to recover a witness for a false statement.

But false means no valid witness exists. That is impossible.

Therefore knowledge error below \(1/3\) contradicts the stipulated soundness failure. \(\square\)

HW3 · Problem 1(b)

Can NIZK for every NP language exist without a random oracle?

The original question concerns non-interactive zero-knowledge proofs for NP in the standard model. Explain why the presence or absence of a setup string matters.

Work through the setup distinction

First distinguish two settings. The plain model has no trusted setup string and no random oracle. The common reference string (CRS) model supplies public information prepared during setup. Both can be called standard-model settings when no random oracle is assumed.

Why is the plain model difficult? Suppose every NP language had a plain-model NIZK. The zero-knowledge simulator could generate a plausible proof for a true statement without its witness. We could run this simulator on an input \(x\) and then run the verifier. On true inputs, the simulation and completeness guarantees would make it accept with high probability. On false inputs, soundness would prevent an efficient simulator from producing an accepted proof except with small probability.

That would give a randomized polynomial-time decision algorithm for every NP language—formally \(\mathrm{NP}\subseteq\mathrm{BPP}\), where BPP means bounded-error probabilistic polynomial time. Such a collapse is not expected, although it has not been proved impossible.

With a suitable CRS, standard-model NIZK for NP is possible under cryptographic assumptions.

So “no random oracle” by itself is not an impossibility argument. We must say whether trusted common setup is allowed. \(\square\)

HW3 · Problem 1(d)

Does Fiat–Shamir always give statistical zero knowledge?

True or false: applying Fiat–Shamir to a Sigma protocol always makes it statistically zero-knowledge.

Show why this is false

False. A Sigma protocol may provide only computational honest-verifier zero knowledge: an efficient observer cannot distinguish its real transcript from a simulated one. Statistical zero knowledge is stronger, requiring even an unlimited observer to see almost the same distributions.

Fiat–Shamir changes how the challenge is chosen. It doesn't erase information in the transcript, and it doesn't by itself strengthen computational privacy into statistical privacy.

The conclusion is false because the transformation supplies no proof of the stronger statistical guarantee. \(\square\)

Homework: one bit isn't enough

If a verifier asks one yes-or-no challenge, a cheater who can answer only one of the two questions may still succeed half the time. Hashing the question doesn't change that. We need to make the whole challenge harder to answer by guessing.

HW3 · Problem 3(a)

Why doesn't direct Fiat–Shamir fix soundness?

A Sigma protocol has a cheating strategy for a false statement that succeeds with probability \(1/2\) against a random one-bit challenge. Show that directly applying Fiat–Shamir does not give negligible soundness error.

Follow the cheating attempt

The cheater prepares its first message \(u\) using the given strategy. Only after \(u\) is fixed does it query \(c=H(x,u)\). In the random-oracle model, that answer is a uniform challenge bit, just as in the original verifier's challenge step.

The cheater replies using the given strategy. The challenge distribution hasn't changed, so the strategy still succeeds with probability \(1/2\).

A constant \(1/2\) chance is not negligible, so this is not a sound non-interactive argument. We used the problem's actual cheating strategy; the mere upper bound “at most \(1/2\)” would not prove such a strategy exists. \(\square\)

HW3 · Problem 3(b)

Make the error negligible, then remove interaction

Starting from a one-bit-challenge Sigma protocol with special soundness, construct a three-message protocol with negligible soundness error. Then make it non-interactive.

Build it and count the answerable challenges

Run \(\lambda\) copies in parallel. Send all \(\lambda\) first messages at once. The verifier returns a vector of \(\lambda\) independently random challenge bits. The prover sends all responses. Accept only if every copy passes. These are still three messages, each containing a batch.

Why does this work on a false statement? Fix the entire batch of first messages. In any one copy, if a dishonest prover could answer both challenges 0 and 1 for the same first message, special soundness would extract a witness for that false statement. There can be no witness. So each copy can answer at most one of its two challenges.

That means the complete batch can answer at most one challenge vector out of \(2^\lambda\) equally likely vectors. Therefore

\[\boxed{\Pr[\text{false acceptance}]\le2^{-\lambda}.}\]

This argument does not assume the cheating prover made its initial messages independently. We fixed the whole batch before counting the possible challenges.

Now apply Fiat–Shamir to the whole batch: hash the public statement and all first messages to get the \(\lambda\)-bit challenge vector. Publish those first messages and all responses. The verifier recomputes the vector and checks every copy.

In the random-oracle model, a polynomial number of tries at different first-message batches still gives only a negligible probability of finding a batch whose hashed challenge can be answered.

This closes both parts of the question. Parallel repetition makes the answerable portion of the challenge space exponentially small; Fiat–Shamir then removes the message that carried that challenge, without enlarging the cheating chance to a constant. \(\square\)

Choose the number of challenge bits. For a false statement with special soundness, a fixed first-message batch can answer at most one entire vector.

Homework: remove the challenge from our PCP argument

Earlier we made a three-message PCP argument using a Merkle tree. The verifier still had to send the random test positions. Now we know how to make those positions reproducible from a hash.

HW3 · Problem 4(b) · Original task

Convert the succinct argument from Problem 4(a) into a non-interactive argument in the random-oracle model.

Build the one-message argument

The prover first computes the full PCP string \(\pi_{\mathrm{PCP}}\) and commits to it with Merkle root \(c\). It then derives the random coins for all \(\lambda\) PCP tests by hashing the public statement, the root, and protocol parameters:

\[\rho=H_{\mathrm{challenge}}(\operatorname{Encode}(x,c,\mathrm{params})).\]

The deterministic PCP query algorithm turns these coins \(\rho\) into the requested proof positions. The prover sends a single proof string containing the root \(c\), the requested bits, and their Merkle authentication paths.

The verifier takes \(x\) and \(c\), computes the same \(\rho\), derives the same positions, verifies all authentication paths, and runs every PCP test.

Completeness: honest PCP bits pass every test, honest paths reconstruct the committed root, and both parties compute the same challenges.

Soundness: the prover must fix \(c\) before the hash determines the test positions. Except with negligible probability of breaking Merkle binding, its openings refer to one fixed encoded proof. For a false statement, the amplified PCP test passes that proof with probability at most \(2^{-\lambda}\). Trying at most polynomially many commitments increases this bound only by a polynomial factor (plus negligible cryptographic failure), which remains negligible.

Proof size: the root uses \(\lambda\) bits; the \(O(\lambda)\) openings use \(O(\lambda\log M)\) bits each. As before, total communication is \(O(\lambda^2\log M)=O(\lambda^2\log n)\), since \(M=\operatorname{poly}(n)\).

We have removed the verifier's message without sending the complete PCP proof. The root fixes the proof before the test is chosen, and the hash lets anyone reconstruct that test. This gives a succinct non-interactive argument; zero knowledge and knowledge extraction have not been established. \(\square\)

For PCPs, the verifier asks for individual bits. PLONK instead makes the verifier ask for polynomial values. The idea remains the same: first construct a test that works with an ideal oracle, then use cryptography to make the oracle's answers trustworthy.
