How could you trust a result without doing the work?

Suppose someone tells you they have carried out a long calculation correctly. You could redo it. But then the proof has saved you nothing. We need another way to be convinced.

Let's begin with a calculation so small that we can see every step. Start with the numbers 0 and 1. The rule is simple: to get the next number, add the previous two.

Step 00Step 11Step 21Step 32Step 43Step 55

For instance, the value at step 3 is \(1+1=2\); the value at step 4 is \(1+2=3\). The final number at step 5 is \(2+3=5\). This is the Fibonacci rule, but nothing about the following method depends on the sequence having a special name.

Now imagine there are a million steps instead of six. A server does the calculation and announces the final number. You know the two starting values, the rule, and the claimed answer. Do you have to repeat a million additions to check it?

Separate what is claimed from what would prove it

The public statement is what we are being asked to believe: “Starting with 0 and 1, applying the rule up to step 5 gives the final result 5.” Call this statement \(x\). The letter is only a name for all that public information, not another number in the sequence.

The server could give us the intermediate results—1, 2 and 3. Call that evidence \(w\), the witness. With the two starting numbers, those intermediate values and the claimed final result, we could check every addition. A checking procedure \(R(x,w)\) would return 1 if all the additions are correct, or 0 if any one is wrong.

\[R(x,w)=1\quad\text{means “the evidence verifies the public claim.”}\]

For the six-value example, we can check \(w\) almost instantly. For a million-step calculation, \(w\) might be huge. Sending all that evidence and checking every transition is precisely the work we wanted to avoid.

What would a shorter proof have to accomplish?

Let's call the short evidence we'd like the server to send \(\pi\), pronounced “pi.” It isn't the witness itself; it is a new object we haven't figured out how to construct yet. We want two things. If the calculation is correct, the server should be able to convince us. If the claimed answer is wrong, a cheating server should have almost no chance of convincing us.

Those two requirements have names: completeness for accepting an honest proof, and soundness for rejecting a false claim. The important thing is that a real proof system must justify both guarantees; merely sending a confident-looking \(\pi\) is worthless.

The problem we have actually reached

We can verify a calculation by checking its whole witness, but the cost grows with the number of steps.

Could we do better by checking just one randomly chosen step of the server's work?

What if we check just one step?

Let's try the obvious shortcut before inventing any cryptography. Ask the server for its intermediate values, then check only one randomly chosen addition. Would that catch a false final answer?

Imagine the server claims the final answer was 8 instead of 5. It sends the values 0, 1, 1, 2, 3, 8. The first three additions are still correct; only the last one is wrong.

Step 00 + 1 = 1Correct
Step 11 + 1 = 2Correct
Step 21 + 2 = 3Correct
Step 32 + 3 ≠ 8Wrong

There are four additions for the verifier to choose from, and only the last one reveals the lie. If we choose a step uniformly at random—so each of the four steps is equally likely—we catch this particular cheat with probability \(1/4\). We miss it with probability \(3/4\).

Now make the calculation longer. If there are \(n\) additions and a cheater changes only one, one random check catches the error with probability just \(1/n\). As \(n\) grows, that probability gets worse. Sampling a few entries of an ordinary computation trace is not enough.

We need a short question—and a meaningful one

There is no difficulty naming one position in a long list. If there are \(2^k\) positions, then \(k\) binary digits are enough to name one of them. For example, 3 digits give eight addresses, from 000 to 111. We call \(k\) the number of address digits.

But a short address is not a proof. In our experiment the verifier asked a short question, and still missed the lie three-quarters of the time. We need to change how the evidence is written so that checking a few carefully chosen places gives a trustworthy answer.

What failed?

Our random check read the ordinary sequence. A single false step could hide among many correct ones.

Could we encode the evidence differently, so a verifier could check just a few places and still have a strong guarantee against cheating?

The main story · 03 of 12

What would make a few checks enough?

We just saw that sampling the original calculation is unreliable. But perhaps the server could write the evidence in a special form, with enough structure that an error is hard to hide from a few random checks.

That's the surprising content of the PCP theorem. For any statement whose witness can be checked efficiently, there is a specially encoded proof that a verifier can check by reading only a few of its bits—three in the formulation used by our lecture.

This theorem is not saying that three bits of our original Fibonacci list are enough. We have just proved the opposite for a simple cheating example. It says a different encoding exists for which three queried bits, chosen according to the verifier's prescribed randomized test, can be enough to obtain a useful error bound.

Exactly what is promised?

If the public statement is true, an honest encoding passes every test. If it is false, any fixed encoded proof string passes a randomly chosen test with probability at most \(1/2\). The course takes this deep theorem as a given; we will not pretend the little Fibonacci example proves the theorem.

\[ \Pr[\text{accept}\mid\text{true statement}]=1,\qquad \Pr[\text{accept}\mid\text{false statement}]\le\tfrac12. \]

Why insist that the proof string is fixed? Suppose the cheater could wait to see which bits we asked for and then invent those bits to make the test pass. There would be no single encoded proof for the theorem to apply to. So the usual picture is a locked box: the whole encoded string is placed inside, and the box reveals only the requested positions.

The two ingredients must not be confused. The PCP encoding is what makes a few checks meaningful. The locked box is what makes the answers refer to one unchanged encoding. The theorem needs both parts of the experiment.

How do we make a one-half error smaller?

Let the verifier repeat the local test \(t\) times with fresh independent randomness, always against the same fixed encoded proof. It accepts only if all tests pass. A false statement then passes with probability at most

\[(1/2)^t=2^{-t}.\]
Repeat the test against one fixed proof

The number shown is the upper bound proved by the PCP guarantee, not an artificial measurement.

There's one difficulty left. The box is imaginary. Sending the entire encoded proof to the verifier would lose the size advantage. We need to fix the long string with a small commitment and then prove that any opened bit really belongs to it.

What did the PCP theorem buy us?

It supplied a special encoding with a proved local test. The ordinary-trace sampling problem has been solved in the ideal locked-box model.

How can a tiny root lock a huge proof?

We need the verifier to inspect bits from one fixed PCP proof. A Merkle tree does exactly that: it commits to an entire list with one short hash, then authenticates any selected position.

Suppose the encoded PCP proof has \(M\) bits. We call its bit at position \(i\) by \(\pi_i\). A hash function \(H\) takes an input and returns a short digest of \(\lambda\) bits. The cryptographic assumption we need is that finding two different inputs with the same digest—a collision—is computationally infeasible.

Hash the individual proof bits to make the leaves of a binary tree. Hash each neighboring pair to make its parent. Continue until one hash remains. Call that final hash \(c\), the commitment root. The prover sends \(c\) before learning the verifier's requested positions.

Prove one bit belongs to the committed list

Blue marks the path the verifier reconstructs; amber marks the hashes the prover must reveal.

Why not send all the leaves? Because to reconstruct a root from one leaf, we need just one neighboring hash at every level. A tree of \(M=2^k\) leaves has \(k=\log_2 M\) levels. So one opening needs \(k\) sibling hashes, or \(O(\lambda\log M)\) bits. The root itself is only \(\lambda\) bits.

Why can't the prover change a bit after committing?

Suppose it could open the same position to both 0 and 1 under the same root. Starting from the two different bit values, follow the two proposed hash paths upward. If the leaf hashes already agree, we have a hash collision. Otherwise the computations differ at the leaf but end at the same root; at some level two different child inputs must therefore produce the same parent hash. That is also a collision.

Our collision-resistance assumption makes this infeasible. So, except with negligible cryptographic failure, the root fixes every bit at every position. This is called position binding.

The root gives the fixed-box behavior the PCP verifier needed, while the logarithmic authentication paths let it read a few positions without receiving the full proof. \(\square\)

Now put PCP and Merkle together

The prover constructs its encoded PCP proof and sends its Merkle root. The verifier then chooses positions for \(t\) independent PCP tests. The prover opens the requested positions with Merkle paths. Finally, the verifier authenticates the opened bits and runs the PCP tests on them.

These checks do different jobs. Merkle authentication says “these bits come from the committed string.” The PCP test says “a fixed string for a false statement is unlikely to pass.” Together they give an error bound of \(2^{-t}+\operatorname{negl}(\lambda)\), where the second term accounts for the tiny chance of breaking the hash commitment.

If each PCP test uses a fixed number of bit queries and we choose \(t=\lambda\), there are \(O(\lambda)\) openings. Their total path size is \(O(\lambda^2\log M)\) bits. The communication is small compared with the full proof for sufficiently large \(M\).

We've built a succinct interactive argument. It is still interactive because the verifier sends its random queries. We'll return to how to remove that message.

Where are we?

We found one valid route: specially encoded PCP bits, fixed by a Merkle commitment. It answers the question of how a few authenticated bit queries can be convincing.

Our calculation itself is arithmetic, however. Can we check the additions directly, rather than relying on a general-purpose PCP encoding? We'll try a second route to the same goal, using polynomials.

Could we check the arithmetic itself?

The PCP route encodes a proof so that a few bits can be checked. But our example has more structure: every new number is the sum of two earlier numbers. Perhaps we can describe all those additions with a single mathematical equation.

Return to the very same six values:

Position \(i\)012345
Claimed value011235

Imagine a polynomial \(f(X)\)—an expression made of powers of a variable \(X\), like \(3X^2+X+1\). We'd like to arrange for \(f(0)=0\), \(f(1)=1\), \(f(2)=1\), and so on up to \(f(5)=5\). Then asking for the value of the computation at position \(i\) would amount to asking for \(f(i)\).

Can we always make such a polynomial?

Start with just the first three values. One polynomial that gives 0, 1 and 1 at positions 0, 1 and 2 is

\[f_2(X)=\frac{X(3-X)}2.\]

Check: at \(X=0\) it is 0. At \(X=1\) it is \((1)(2)/2=1\). At \(X=2\) it is \((2)(1)/2=1\). This polynomial was chosen to fit only the first three positions; we haven't yet fitted all six.

Making a polynomial fit a given list of values is called interpolation. For any six distinct input points in a field, there is exactly one polynomial of degree at most five that fits six prescribed outputs. We'll establish the reason for uniqueness in the next lesson, using a fact about polynomial roots.

Why are we using a field?

Cryptographic polynomial protocols work with a finite field, a number system where we can add, multiply and divide by any nonzero number. For this small example use \(\mathbb F_{101}\): the integers 0 through 100, with results taken modulo 101. Because 101 is prime, every nonzero element has a multiplicative inverse.

For example, dividing by 2 makes sense because \(2\cdot51=102\equiv1\pmod{101}\), so 51 acts as \(1/2\) in this field. Our six small Fibonacci values are unchanged by reducing modulo 101.

Let \(f(X)\) now mean the unique degree-at-most-five polynomial matching all six values. The prover could fix that polynomial and let the verifier request evaluations, instead of handing over a long list of numbers.

But notice what we've not achieved. A dishonest prover could just as easily interpolate the false list 0, 1, 1, 2, 3, 8. Interpolation turns a list into a polynomial; it does not check whether the list is true.

What did interpolation solve?

We have one object that records the calculation's values, and a way to retrieve any value by asking \(f(i)\).

Why should checking an equation once tell us anything?

We want to check polynomial equations at a randomly chosen number. But different polynomials can agree at some points. So the whole method rests on one question: how many points could fool us?

Take two polynomials \(f(X)\) and \(g(X)\), each of degree at most \(d\). If they are identical, their values agree at every \(X\). If they differ, subtract them and call the difference \(h(X)=f(X)-g(X)\). Then \(h\) is a nonzero polynomial of degree at most \(d\). The test \(f(r)=g(r)\) accepts a false claim exactly when \(h(r)=0\).

So everything depends on how many roots—a root is an input that makes a polynomial zero—a nonzero degree-\(d\) polynomial can have.

Why there can be at most \(d\) distinct roots

Suppose \(h(a)=0\). We can factor \(h(X)\) as \((X-a)q(X)\). Why? For each power, \(X^j-a^j\) contains the factor \(X-a\) (for example \(X^2-a^2=(X-a)(X+a)\)). Thus \(h(X)-h(a)\) contains that factor; since \(h(a)=0\), so does \(h(X)\).

Now let \(b\ne a\) be another root. Substituting \(b\) into the factorization gives \(0=(b-a)q(b)\). The first factor is nonzero, and in a field two nonzero numbers cannot multiply to zero. Therefore \(q(b)=0\). The remaining roots still belong to the quotient.

Each distinct root therefore contributes a new factor \((X-a)\), lowering the degree of what remains by one. A nonzero degree-\(d\) polynomial cannot have more than \(d\) such factors.

Thus a nonzero polynomial of degree at most \(d\) has at most \(d\) distinct roots. \(\square\)

Now go back to the equality test. If the verifier chooses \(r\) uniformly from a field of \(p\) elements, at most \(d\) of those \(p\) choices can make a false polynomial equality look true. Hence

\[\Pr[f(r)=g(r)\mid f\ne g]\le \frac{d}{p}.\]
Find the random values that fool the verifier

Use \(\mathbb F_{101}\). The two polynomials differ by \((X-1)(X-4)\), so they agree only when that difference is zero.

This also completes a claim we made about interpolation. If two degree-at-most-five polynomials agreed at the six distinct positions 0 through 5, their nonzero difference would need six roots, which is impossible. So the polynomial representing our six values is unique.
