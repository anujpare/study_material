Lecture §5 · The PLONK IOP

Fibonacci was one calculation. What about every calculation?

Our Fibonacci proof worked because every step obeyed the same rule: add the previous two values. But a general program might add at one step, multiply at another, and reuse an earlier result many times. If we want a SNARG for general NP statements, we need a standard way to describe those calculations.

That's what an arithmetic circuit provides. Think of a computation drawn as boxes connected by wires. Each box, called a gate, receives two field values and either adds or multiplies them. The wires carry outputs of earlier gates to later ones. The circuit tells us exactly which calculation must take place.

The lecture defines an arithmetic circuit \(C\) over a field \(\mathbb F\), with two kinds of inputs: public values \(\mathbf x\), known to the verifier, and private values \(\mathbf w\), known to the prover. The bold notation means an ordered list of numbers, called a vector.

Rather than proving the output equals an arbitrary target directly, the lecture uses the equivalent zero-output form: the prover must show that some private witness makes

\[\boxed{C(\mathbf x,\mathbf w)=0.}\]

We can write the set of true statements as

\[L=\{\mathbf x\in\mathbb F^m:\exists\mathbf w\in\mathbb F^n,\ C(\mathbf x,\mathbf w)=0\}.\]

Why does this help with the NP statements from the very first lesson? Remember the ordinary checker \(R(x,w)\), which returned 1 for a valid witness. If we know how to check the witness by a finite sequence of steps, we can draw those steps as a circuit: inputs are the public statement \(x\) and witness \(w\), and each elementary operation becomes a gate. Instead of asking whether the checker returns 1, we can subtract 1 at the end and ask whether the resulting circuit outputs zero. So the circuit statement is a new representation of the original witness-checking problem, not a different problem.

For Boolean checks this translation is especially concrete. In the field \(\mathbb F_2\), where 0 and 1 are the only elements, multiplication acts as AND and addition acts as XOR. NOT of a bit \(a\) can be written \(1+a\), and OR of bits \(a,b\) can be written \(a+b+ab\), all modulo 2. Thus ordinary Boolean verification logic can be assembled from additions and multiplications. We use the same arithmetic-circuit idea over larger fields for the polynomial proofs.

Work through the lecture's three-gate example

Take public inputs \(x_1=2\) and \(x_2=4\), and private input \(w_1=3\). The circuit performs

\[t=(x_1x_2)(x_2+w_1).\]

Gate 0 multiplies \(2\cdot4=8\). Gate 1 adds \(4+3=7\). Gate 2 multiplies the two intermediate outputs, giving \(8\cdot7=56\). Here's the complete proposed gate table:

GateOperationLeftRightOutput
0Multiply248
1Add437
2Multiply8756

Notice an apparent mismatch: the example outputs 56, but the formal language above requires output 0. This pictured circuit is an illustration of an execution, not yet a satisfying zero-output instance. If our public claim is “the result is 56,” we can add a final comparison \(t-56=0\). That makes a new circuit whose final output is zero. We'll keep the original three-gate circuit for the lecture's trace-encoding example, and distinguish its illustrative target check from the general zero-output requirement.

Why is a list of correct gates not enough?

Suppose gate 0 outputs 8, but gate 2 secretly uses 9 as its left input. Gate 2 might still multiply its two inputs correctly, yet the entire circuit would be wrong: the wire connecting gate 0 to gate 2 was not respected.

To verify a circuit, then, we must check both the arithmetic inside each gate and the values copied along the wires, along with the public inputs and final output. The proposed values of all inputs and wires form the circuit trace.

We can now reduce general computation to a long list of simple gate equations. But if the verifier checks each gate and wire directly, it has to follow the entire computation again. We need the polynomial trick from Fibonacci: encode all the claimed trace values in one polynomial, then express the circuit rules as polynomial identities.

Lecture §5.1 · From Circuits to Polynomials

How can one polynomial remember every gate value?

The circuit has given us a collection of claimed input, intermediate and output values. Our efficient verifier knows how to ask a polynomial oracle for evaluations. So we'll use interpolation—exactly as in Fibonacci—to turn the entire trace into one polynomial.

First count the numbers we have to store. Every gate gives us three values: its left input, right input and output. There are \(|C|\) gates, where \(|C|\) means the number of gates. There are also \(|I|\) original inputs, including public and private ones. So the total number of trace entries is

\[\boxed{d=3|C|+|I|.}\]

In the three-gate example, \(|C|=3\), and the original inputs are 2, 4, 3, so \(|I|=3\). Thus \(d=3\cdot3+3=12\) values. Those twelve values are what our polynomial must remember.

Which twelve points should hold the numbers?

We could choose any twelve different field elements. But the lecture makes a special choice that will simplify verification later. Pick a number \(\omega\) with multiplicative order 12. That means \(\omega^{12}=1\) but no smaller positive exponent gives 1. Then the twelve points

\[\Omega=\{1,\omega,\omega^2,\ldots,\omega^{11}\}\]

are all distinct: if two powers repeated before exponent 12, a smaller positive power would equal 1. The lecture calls such an \(\omega\) a root of unity.

For a small numerical example, work in \(\mathbb F_{97}\), the integers modulo 97. Here \(\omega=6\) has order 12. In fact \(6^6\equiv96=-1\), so \(6^{12}\equiv1\); and \(6^4\equiv35\ne1\). These rule out all proper divisors of 12 as possible orders.

See the twelve different evaluation points

Move the exponent \(j\) and watch \(6^j\bmod97\) visit each point. After \(j=11\), the next power returns to 1.

Assign every trace entry to a point

Now the prover interpolates a polynomial called \(f_{\rm trace}(X)\) through these twelve values. We assign the original inputs to the last few powers, using \(\omega^{-j}=\omega^{12-j}\), and assign the three values of gate \(l\) to three successive powers beginning at \(\omega^{3l}\):

\[ \begin{aligned} f_{\rm trace}(\omega^{-j})&=\text{original input number }j,\\ f_{\rm trace}(\omega^{3l})&=\text{left input of gate }l,\\ f_{\rm trace}(\omega^{3l+1})&=\text{right input of gate }l,\\ f_{\rm trace}(\omega^{3l+2})&=\text{output of gate }l. \end{aligned} \]

Here \(j=1,\ldots,|I|\) and \(l=0,\ldots,|C|-1\). These are not mysterious shifts: they are a filing system. Three consecutive evaluation points store the three numbers for one gate.

Trace itemEvaluation positionsStored values
Original inputs\(\omega^{-1},\omega^{-2},\omega^{-3}\)2, 4, 3
Gate 0: multiplication\(\omega^0,\omega^1,\omega^2\)2, 4, 8
Gate 1: addition\(\omega^3,\omega^4,\omega^5\)4, 3, 7
Gate 2: multiplication\(\omega^6,\omega^7,\omega^8\)8, 7, 56

Does the trace polynomial actually exist?

Yes. We prescribed exactly twelve values at twelve distinct field points. The interpolation construction gives a polynomial of degree at most 11 matching them. And if two such polynomials matched at all twelve points, their difference would have twelve roots but degree at most 11, so it would have to be zero. Thus the interpolating polynomial is unique.

The prover can represent the complete proposed trace with one degree-at-most-11 polynomial. The lecture sometimes uses the looser degree bound \(d=12\), but degree 11 suffices for this interpolation. \(\square\)

There is an important limitation: any twelve numbers can be interpolated, including a dishonest trace. Our polynomial is a representation, not yet evidence of correctness.

Why did we choose the awkward powers of \(\omega\) instead of the natural indices 0 through 11? Because the polynomial that vanishes at all these powers has a special simple formula. That will help us avoid the slow product that troubled the Fibonacci verifier.

Lecture §§3 and 5.2 · Efficient vanishing polynomials

Why use these special evaluation points?

The Fibonacci verifier had one remaining expensive calculation: evaluating a vanishing polynomial that was a product of many factors. We have now chosen the trace positions to be all the powers of a root of unity. That makes their vanishing polynomial much easier to evaluate.

For the entire set \(\Omega=\{1,\omega,\ldots,\omega^{d-1}\}\), the vanishing polynomial is, by definition,

\[Z_\Omega(X)=\prod_{j=0}^{d-1}(X-\omega^j).\]

There are \(d\) factors. But every point \(\omega^j\) also makes the much simpler polynomial \(X^d-1\) equal to zero, because \((\omega^j)^d=(\omega^d)^j=1\).

Show that the two polynomials are identical

Both polynomials have degree \(d\) and leading coefficient 1. Their difference therefore has degree at most \(d-1\): the leading \(X^d\) terms cancel.

Yet at each of the \(d\) distinct points \(\omega^0,\ldots,\omega^{d-1}\), both polynomials are zero, so their difference has \(d\) roots. A nonzero polynomial of degree at most \(d-1\) cannot have that many roots. Their difference must therefore be identically zero.

\[\boxed{Z_\Omega(X)=X^d-1.}\]

That is why we chose this domain: a vanishing product with \(d\) factors collapses to a single power and a subtraction. \(\square\)

Doesn't taking a large power also take a long time? Not with repeated squaring. To calculate \(r^{12}\), first calculate \(r^2\), then \(r^4\), then \(r^8\), and multiply \(r^8r^4\). That's four field multiplications, rather than evaluating and multiplying twelve separate factors. In general, exponentiation by repeated squaring takes \(O(\log d)\) multiplications.

One caution: the identity \(Z_\Omega(X)=X^d-1\) is for the full roots-of-unity domain. A smaller set of positions—such as just the public-input positions or just gate starts—does not automatically have that same polynomial. The lecture notes that these subsets can also have useful structure or be handled with circuit-specific preprocessing; it does not provide every resulting formula.

We now have a convenient polynomial encoding of the trace and a fast way to evaluate the full-domain vanishing polynomial. The next question is the one that actually determines correctness: what equations must that trace satisfy so it represents the circuit we asked the prover to run?

Lecture §5.2 · Verifying the circuit trace, conditions 1–2

How do we know the trace is for our statement?

The prover has committed to a polynomial representing twelve numbers. But interpolation would have produced a polynomial for any fabricated table. We need conditions that force these numbers to describe an execution of the public circuit, with the public inputs the verifier supplied and the required output.

The lecture lists four requirements: the final output, the public inputs, correctness of every gate, and consistency of the wires. We'll handle them one at a time. The first two anchor the trace to the particular statement we're proving.

1. The circuit must reach the required output

For gate \(l\), the output is stored at \(f_{\rm trace}(\omega^{3l+2})\). The last gate has number \(|C|-1\), so its output is at exponent \(3(|C|-1)+2=3|C|-1\).

For the lecture's zero-output circuit statement, this means checking one value:

\[\boxed{f_{\rm trace}(\omega^{3|C|-1})=0.}\]

The lecture's pictured three-gate circuit ends in 56, not 0. If we use that picture to claim its output is 56, the corresponding illustrative condition is \(f_{\rm trace}(\omega^8)=56\). To use the formal zero-output language, append a target-checking operation and build the trace and evaluation domain for that modified circuit. We must not mix the three-gate positions with the four-gate output check.

2. The prover must not change our public inputs

Suppose the verifier specified public inputs \(x_1,\ldots,x_m\). The trace has designated positions \(\omega^{-1},\ldots,\omega^{-m}\) for them. The verifier must make sure the prover really put the requested values there.

Construct a polynomial \(f_{\rm in}\) from the public data, with \(f_{\rm in}(\omega^{-j})=x_j\) at each public-input position. This is ordinary interpolation: the verifier knows those values and therefore knows the intended polynomial. It need not know the private witness.

Define the difference

\[g(X)=f_{\rm trace}(X)-f_{\rm in}(X).\]

At public-input position \(\omega^{-j}\), the equation \(g(\omega^{-j})=0\) means exactly \(f_{\rm trace}(\omega^{-j})=x_j\). Thus all the public inputs are correct if and only if \(g\) is zero on the set \(\Omega_I=\{\omega^{-1},\ldots,\omega^{-m}\}\).

That is ZeroTest again. The prover supplies the polynomial \(g\) and its vanishing-polynomial quotient. Before using ZeroTest, the verifier checks that the claimed \(g\) is actually consistent with \(f_{\rm trace}-f_{\rm in}\), by a random equality test using authenticated evaluations. Otherwise the prover could substitute an unrelated polynomial that happens to vanish on \(\Omega_I\).

What do these first two checks establish?

The first check pins down the final result. The second pins down every public input. A successful ZeroTest of \(g\), together with the consistency check, forces \(f_{\rm trace}(\omega^{-j})=x_j\) at each public-input position.

We now know the trace begins with the right public values and claims the right final answer. We do not yet know whether it reached that answer by performing the correct operations. \(\square\)

Why not just open all \(m\) input locations directly? Because that would require \(m\) separate authentication proofs and make the proof length grow linearly with the public input. The verifier may spend time reading the public input, but the SNARG proof itself must remain succinct.

Correct endpoints aren't enough. A prover could put the right public inputs and right answer in its trace but invent arbitrary intermediate values. Next we must force every individual gate to perform the operation shown in the public circuit.

Lecture §5.2 · Verifying the circuit trace, condition 3

How can one equation check both addition and multiplication?

The verifier must reject a trace with a wrong gate result. But there may be millions of gates. If it checked each one separately, we would be back to repeating the computation. We need one polynomial whose required zeros express all the gate calculations.

Start with just one gate. Call its left input \(L\), its right input \(R\), and its output \(O\). For addition we need \(L+R=O\). For multiplication we need \(LR=O\).

The circuit already tells us which operation each gate performs. Encode that public choice with a bit \(s\), called a selector: set \(s=1\) for addition and \(s=0\) for multiplication. Now consider

\[\boxed{s(L+R)+(1-s)LR-O=0.}\]

Substitute \(s=1\): the multiplication part disappears, leaving \(L+R-O=0\). Substitute \(s=0\): the addition part disappears, leaving \(LR-O=0\). So the same equation checks either kind of gate exactly.

Look at the lecture's example. Gate 0 multiplies \(2\cdot4=8\), so \(s=0\) and the equation becomes \(2\cdot4-8=0\). Gate 1 adds \(4+3=7\), so \(s=1\) and it becomes \(4+3-7=0\). The formula doesn't merely resemble the right rules; it gives them exactly.

Use the trace polynomial instead of three separate numbers

Recall our encoding: at gate-start point \(X=\omega^{3l}\), the left input is \(f_{\rm trace}(X)\), the right input is \(f_{\rm trace}(\omega X)\), and the output is \(f_{\rm trace}(\omega^2X)\). The public circuit also determines the selector for each gate.

Interpolate those selector bits into a polynomial \(f_{\rm sel}(X)\) with \(f_{\rm sel}(\omega^{3l})=0\) for multiplication and 1 for addition. For the three-gate example, its values at gate starts \(1,\omega^3,\omega^6\) are 0, 1, 0.

Now replace \(L,R,O,s\) in the single-gate equation with these polynomial evaluations:

\[ \begin{aligned} f_{\rm gates}(X)={}&f_{\rm sel}(X)\bigl(f_{\rm trace}(X)+f_{\rm trace}(\omega X)\bigr)\\ &+\bigl(1-f_{\rm sel}(X)\bigr)f_{\rm trace}(X)f_{\rm trace}(\omega X)\\ &-f_{\rm trace}(\omega^2X). \end{aligned} \]

Why is this useful? At the start of any gate \(l\), the equation \(f_{\rm gates}(\omega^{3l})=0\) is exactly the correct arithmetic rule for that gate. Hence every gate is evaluated correctly if and only if the gate polynomial vanishes on

\[\Omega_{\rm gates}=\{\omega^0,\omega^3,\omega^6,\ldots,\omega^{3(|C|-1)}\}.\]

That's the same pattern we proved in Fibonacci: many required zero values, one vanishing-polynomial quotient, and a random ZeroTest to check the identity without visiting every position.

What does this guarantee?

If the gate polynomial is zero at each gate-start point, substituting those points recovers the correct addition or multiplication equation for every gate, because the selector comes from the public circuit. Conversely, if every gate is evaluated correctly, those same equations are zero at every gate-start point.

We have reduced all the local gate checks to a polynomial vanishing condition. But we have not yet proved that one gate used the output of the gate actually wired to it. \(\square\)

The selector polynomial is large—its degree grows with circuit size. The verifier should not calculate it from scratch for every proof. But the selector depends only on the circuit, not on the input or private witness, so it can be computed and committed to in a one-time circuit-specific preprocessing step.

Here's the remaining loophole. Gate 2 could correctly compute \(9\cdot7=63\), even though gate 0 produced 8 and was supposed to feed 8 into gate 2. Every local gate equation might pass while the overall circuit is false. The last condition checks the wires linking the gate rows.

Lecture §5.2 · Verifying the circuit trace, condition 4

Three correct gates can still describe the wrong computation

We have proved that every gate performs its own addition or multiplication correctly. But the trace stores some values more than once. The output of one gate appears again as the input to another. Those repeated entries must agree, or the prover can secretly change a wire value while keeping each individual gate locally correct.

In our original circuit, gate 0 produces 8, and gate 2 must use that 8 as its left input. Gate 1 produces 7, and gate 2 must use 7 as its right input. In terms of the trace polynomial, the required equalities are

\[ f_{\rm trace}(\omega^2)=f_{\rm trace}(\omega^6), \qquad f_{\rm trace}(\omega^5)=f_{\rm trace}(\omega^7). \]

And we must also ensure the original input entries agree with the copies inside the gates. For example, public \(x_2=4\) appears at \(\omega^{-2}\), gate 0's right input at \(\omega^1\), and gate 1's left input at \(\omega^3\). All three places refer to one logical wire and must contain the same number.

Make a trace lie in different ways

Choose a proposed trace. See which checks fail. The simulator includes an extra target-check gate in \(\mathbb F_{97}\) so that the desired final output is zero; this is a gate-value illustration, not the earlier twelve-point polynomial encoding.

How can we describe all wire equalities at once?

Take any logical wire and list every trace position where its value appears. Put those positions in a cycle. For the input \(x_2\), for instance, we can make a cycle through \(\omega^{-2}\), \(\omega^1\), \(\omega^3\), and back to \(\omega^{-2}\).

The lecture encodes the mapping from each position to the next position carrying the same wire using a rotation polynomial \(f_{\rm rot}\). It is a polynomial representation of a permutation of the trace positions, determined entirely by the circuit wiring. It is not merely the operation \(X\mapsto\omega X\).

The intended consistency condition is

\[\boxed{f_{\rm trace}(a)=f_{\rm trace}(f_{\rm rot}(a))\quad\text{for all }a\in\Omega.}\]

Why do these equalities enforce the actual wires?

Suppose one logical wire appears at positions \(a_1,\ldots,a_k\), ordered as a cycle \(a_1\to a_2\to\cdots\to a_k\to a_1\). The displayed equation forces the value at \(a_1\) to equal the value at \(a_2\); that equals the value at \(a_3\), and so on. By ordinary transitivity of equality, every occurrence carries the same number.

Conversely, if each logical wire really does carry one consistent value at every occurrence, then all these equalities hold. So checking these relations is equivalent to checking correct wire copying.

This closes the loophole left by local gate equations. Once wire copies are consistent, the gate calculations refer to the actual connected circuit, not independent rows of arithmetic. \(\square\)

Like the selector polynomial, \(f_{\rm rot}\) depends only on the public circuit, not on its witness. It can therefore be computed and committed to in preprocessing. The lecture explicitly does not give the detailed polynomial IOP for efficiently checking these rotation relations; we should understand the logical condition and its purpose without inventing a full security proof that isn't in the source.

Lecture §6 · A PLONK SNARG

Why do these checks prove the circuit statement?

We started by asking how to verify a long computation without running it again. The trace polynomial now holds a proposed execution, and we have four requirements that aim to force it to be genuine. Before discussing proof size, let's show exactly why passing all four means the public statement is true.

From a valid trace to a satisfying witness

Take a trace that passes all four checks. The public-input check fixes the known inputs to the values the verifier supplied. The other original input positions determine a candidate private witness \(\mathbf w\).

Now process the circuit in gate order. For the first gate, its input wires have definite values. The gate equation forces its output to be the correct sum or product. The wiring check forces every later occurrence of that output wire to carry exactly that same value. So the next gate receives the outputs specified by the circuit, rather than values invented independently by the prover.

Repeat this reasoning through all gates. By induction on the gate order, the whole trace is a genuine evaluation of \(C(\mathbf x,\mathbf w)\). Finally, the output check says that this genuine evaluation reaches zero. Therefore

\[\boxed{C(\mathbf x,\mathbf w)=0.}\]

We have proved the logical implication the protocol needs: if the four constraint families hold, the trace supplies an actual witness to the public circuit statement. This is why checking them is sufficient. \(\square\)

How is the final system organized?

The lecture divides the work into three stages, because some calculations depend only on the circuit, while others depend on the witness for a particular proof.

Universal setup. Run the polynomial commitment scheme's setup to obtain public parameters \(pp\). This setup supports some maximum degree or circuit size but does not depend on a particular circuit \(C\).

Circuit-specific preprocessing. Given \(C\), build its selector polynomial \(f_{\rm sel}\) and rotation polynomial \(f_{\rm rot}\), commit to them, and publish the commitments as part of the circuit's verification information. This step takes work proportional to circuit size \(O(|C|)\) but can be reused for many different inputs to the same circuit.

Proof and verification. For public input \(\mathbf x\) and witness \(\mathbf w\), compute the circuit trace, interpolate and commit to \(f_{\rm trace}\), and produce the polynomial checks summarized below.

The four checks in the lecture's final protocol

1. Output: authenticate the trace polynomial's value at the final gate's output position and check it is zero.

2. Public inputs: construct \(f_{\rm in}\) from the public values, check that the claimed difference \(f_{\rm trace}-f_{\rm in}\) is consistent with the trace, and use ZeroTest over the public-input positions with a quotient polynomial.

3. Gate arithmetic: use the preprocessed selector polynomial and the trace polynomial to form \(f_{\rm gates}\). The prover supplies its vanishing-polynomial quotient over all gate-start positions. The verifier checks the resulting identity using authenticated random evaluations.

4. Wiring: use the preprocessed rotation polynomial to establish that all occurrences of the same logical wire have equal values. The lecture sketches this additional polynomial IOP rather than deriving it completely.

Every random evaluation point that the verifier would choose interactively can then be derived using Fiat–Shamir in the random-oracle model, producing a non-interactive proof string. Which polynomial commitment scheme we select affects setup assumptions and security properties.

Why is it supposed to be succinct?

The prover still performs the full circuit computation and prepares the polynomial commitments and quotients. But the verifier does not inspect every gate. It authenticates a small number of polynomial evaluations and checks a small number of identities.

Let \(|C|\) mean the number of circuit gates, \(|\mathbf x|\) the size of the public input, \(|\pi|\) the proof length, and \(T_V\) the verification time. The lecture's intended bounds are

\[ |\pi|=O\bigl(\lambda,\operatorname{polylog}|C|\bigr), \qquad T_V=O\bigl(\lambda,|\mathbf x|,\operatorname{polylog}|C|\bigr). \]

These are target asymptotic bounds for suitable implementations, not costs derived from our tiny example. Their significance is that the verifier may read the public statement, but it should not redo work proportional to the full circuit.

What does each check rule out?

We should be precise about the scope of the notes. We've explained why the four conditions imply a satisfying circuit execution, the polynomial tools for checking the stated identities, and the commitment/Fiat–Shamir blueprint. The lecture does not fully prove a concrete polynomial commitment construction or its entire wiring IOP, so a complete end-to-end SNARG security theorem needs those additional components.

Nor has the lecture shown that the proof hides the witness. Zero knowledge is a further property that may be added by randomization; it isn't part of the SNARG definition used here.

Return to the original million-step computation. The prover still does the expensive work, but it can encode the execution as a circuit trace, and the verifier can check authenticated polynomial identities rather than recomputing every step. The four constraints are what tie those short checks back to the actual computation. That's the full reason the construction is useful—not just a collection of unrelated polynomial tricks.
