I · Why SNARGs exist · Lecture §1

How can we check a calculation without repeating it?

Suppose a server does a million steps of a calculation and gives you the answer. If checking the answer takes another million steps, what have you gained?

Imagine the server repeatedly applying the same public function \(H\), starting with a value \(a\). After a million steps, it tells you the answer is \(b\). We know the function, the starting value, the number of steps and the claimed result. We do not know whether the server actually performed the steps correctly.

There is an obvious way to check. Ask the server for every intermediate value, then apply \(H\) to each value and see whether the next one matches. This is convincing, but it makes us do nearly the entire calculation ourselves.

Could the server send something much shorter—something we can check quickly, but that a cheater cannot easily fake? That's the problem a succinct proof is meant to solve.

What must the server prove?

Let's give names to the pieces we already have. The statement, written \(x\), is the public claim. In this example, \(x\) contains the starting value \(a\), the reported result \(b\), and the rule to apply \(H\) one million times.

The witness, written \(w\), is the extra evidence that makes the claim checkable. Here, \(w\) can be the list of intermediate values. If we had the list, we could check every step, and that would tell us whether the claimed result is right.

Call this ordinary checking procedure \(R\). We write \(R(x,w)=1\) if all the steps check out, and \(R(x,w)=0\) otherwise. The number 1 simply means “accept.”

A statement is true if at least one valid witness exists. Cryptographers collect all true statements in a set called a language \(L\):

\[L=\{x:\exists w\text{ with }R(x,w)=1\}.\]

The symbol \(\exists\) means “there exists.” So the equation says only this: \(x\) belongs to \(L\) if there is some evidence \(w\) that passes the checker.

We care about problems where checking a supplied witness is efficient, even if finding one is hard. Those are the kinds of problems studied in the complexity class NP. We won't need the complexity theory to follow the next construction; the key point is simply that checking evidence and finding evidence are different jobs.

Who sends what?

The prover, \(P\), knows the witness and wants to convince us. The verifier, \(V\), knows only the public statement and checks the claim. Our goal is for the prover to send a short string, called the proof \(\pi\) (the Greek letter “pi”), instead of the entire witness \(w\).

Prover \(P\)

Has the public claim \(x\) and the long evidence \(w\).

⟶
Verifier \(V\)

Receives a short proof \(\pi\) and checks the claim \(x\).

The long witness stays with the prover. Whether a short proof can replace it is exactly what we still need to establish.

What would make this convincing?

Two things. First, when the claim is true and the prover follows the rules, the verifier should accept. This is completeness. The lecture asks for perfect completeness: an honest proof always passes.

Second, when the claim is false, even a dishonest prover should have only a small chance of making the verifier accept. This is soundness. We call that small chance \(\varepsilon\), the soundness error:

\[ \begin{aligned} \Pr[\text{accept}\mid\text{true, honest prover}]&=1,\\ \Pr[\text{accept}\mid\text{false claim}]&\le\varepsilon. \end{aligned} \]

Here \(\Pr\) means probability; the second guarantee must cover every cheating strategy allowed by the security model. The point is not that a proof looks persuasive. It must come with a reason a false claim is very unlikely to pass.

We now know what we're trying to replace: a long witness \(w\) that we could check ourselves. But if the proof \(\pi\) is just as long as \(w\), we've solved nothing. Next we'll look at what it means for the proof to be short.

How much shorter can a proof be?

The server could send us the whole list of intermediate results. We could check it, but we'd still have a huge amount of work. What does it take to make verification genuinely cheaper?

We called the long evidence \(w\) and the short proof we hope to send \(\pi\). The notation \(|w|\) means the length of the witness in bits, and \(|\pi|\) means the length of the proof in bits. A list of intermediate numbers can always be written as a sequence of 0s and 1s. For example, if the list contains a million 256-bit results, its encoding uses roughly 256 million bits.

Sending \(w\) directly would make the proof as long as the evidence. A succinct proof should instead stay small as the witness becomes large. How could that even be possible? Let's first see one simple reason why a large amount of information needn't always require a large question.

Naming one bit is cheaper than sending every bit

Imagine the witness consists of just eight bits, at positions 0 through 7. To ask for position 5, we don't have to list all eight bits. We can say “101,” because 101 is the number 5 written in binary. Every position from 0 to 7 has a three-digit binary address, from 000 to 111.

Why three digits? A binary digit has two choices, 0 or 1. Three of them give \(2\times2\times2=2^3=8\) different addresses. If there are \(2^k\) positions, \(k\) binary digits can name any one of them. The letter \(k\) here is simply the number of address digits. The inverse statement is written \(\log_2(2^k)=k\), pronounced “log base two.”

How many digits does an address need?

Change \(k\). Each additional binary digit doubles the number of bits we could address. The large number is the length of the imagined witness, not the length of a SNARG proof.

There's a crucial difference between naming a bit and checking a proof. Knowing how to request a few positions doesn't tell us whether those positions are enough to catch cheating. We'll need a theorem for that in the next lesson.

Now define the kind of proof we want

Let \(|x|\) be the length of the public statement. Let \(T_V\) be the time the verifier spends checking the proof. Finally, \(\lambda\) is a security parameter: increasing it is meant to make attacks less likely. The lecture asks for a proof that remains small and a verifier that does little work compared with reading the witness:

\[ |\pi|=O\!\left(\lambda,\operatorname{polylog}(|x|,|w|)\right) \] \[ T_V=O\!\left(\lambda,|x|,\operatorname{polylog}(|w|)\right). \]

Here's what the notation is saying. A polylogarithm is a fixed power of a logarithm, such as \((\log_2 n)^2\). The \(O\) notation describes how a cost grows, rather than an exact byte count. So the proof and its verification should depend on the very large witness mainly through logarithms, not by reading it all. The verifier may still need time proportional to \(|x|\) to read the public claim.

And why “non-interactive”?

If the verifier must send a fresh random question and wait for the prover's answer, the parties are still having a conversation. A non-interactive proof is one string the prover can send now and anybody can check later, without contacting the prover.

Put the requirements together and we get a SNARG: a Succinct Non-Interactive Argument. “Argument” means that resistance to cheating relies on computational assumptions: we promise security against attackers with realistically bounded computing power, not an infinitely powerful attacker.

A SNARG need not hide the witness. That stronger privacy property is called zero knowledge. Nor does the word SNARG alone promise a way to extract a witness from a successful prover.

We've seen why a question about a huge bit string can be short. Now for the difficult part: can we arrange a proof so that checking only a few chosen bits really tells us something about the whole statement? That's where the PCP theorem enters.

Could checking just three bits catch a false proof?

We just learned to name a position in a long string using few bits. But if you inspected three random characters of an ordinary calculation, you probably wouldn't learn whether it was correct. The next theorem solves that harder problem.

The PCP theorem says that the prover can write the evidence in a special encoded form so that a verifier can check a statement by reading only three bits of this encoded proof. The encoding is important: three bits of the original witness would not normally be enough.

Let's call the long encoded bit string \(\pi_{\rm PCP}\), to distinguish it from the short SNARG proof \(\pi\) we eventually want. Let \(M\) be the number of bits in \(\pi_{\rm PCP}\). This is a new length: \(M\) describes the specially encoded PCP proof, while \(|w|\) in the previous lesson described the original witness. They need not be the same size.

We can use what we just learned about binary addresses. Even when the encoded proof has \(M\) bits, choosing a position needs only about \(\log_2 M\) bits. The remarkable new part is that, with this special encoding, inspecting only a constant number of chosen bits can actually detect false claims.

What does the theorem guarantee?

For a true statement, there is an encoded proof that passes every test. For a false statement, every fixed bit string the cheater might offer has at most a one-half chance of passing a randomly chosen test:

\[ \Pr[\text{accept}\mid\text{true statement, honest PCP}]=1, \qquad \Pr[\text{accept}\mid\text{false statement}]\le \tfrac12. \]

The theorem is a deep result, and the lecture asks us to use it rather than prove it. For now, what matters is exactly what it promises—and that the random test is applied to a proof string already fixed by the prover.

Imagine keeping the encoded proof in a locked box

The prover puts all \(M\) bits inside a box and closes it. The verifier can request position \(i\), and the box returns the bit \((\pi_{\rm PCP})_i\). The box always answers from the same string; the prover can't replace a bit after learning the question.

How do we make the error smaller than one-half?

Repeat the test \(t\) times, choosing fresh independent random positions each time, but always testing the same fixed proof. Accept only if every test passes. For a false statement, the chance of passing each independent test is at most \(1/2\), so

\[\Pr[\text{all }t\text{ tests pass}]\le(1/2)^t=2^{-t}.\]

To build a real proof, we still have to replace the imaginary box. Sending all \(M\) bits defeats our aim of a short proof. Asking a dishonest prover for bits without fixing its string lets it change answers to suit our questions. We need a way to lock a long string using one small commitment.

The mathematical verifier works with a locked bit string. Cryptography will now give us a real way to lock the string and open just the positions we ask for.

How can one small value lock a long list?

The PCP prover has already written a long encoded proof. We want the verifier to read a few bits without receiving all of them, while preventing the prover from changing its answers after learning which positions are requested.

We called the length of that encoded proof \(M\) bits. For now, think of it as an ordered list of \(M\) messages, one per position. Call the message at position \(i\) by the name \(m_i\). In our PCP application, each \(m_i\) is just one bit, but a vector commitment can also store larger messages.

A vector commitment makes a short public value \(c\) that fixes the whole list. Later the prover reveals one \(m_i\) and supplies a short opening proof showing that this is the value committed at position \(i\).

What exactly does “fixes” mean? After sending \(c\), a dishonest prover should not be able to open the same position \(i\) once as \(m_i\) and again as a different \(m_i'\), with both openings accepted. This is called position binding. It is precisely the property missing from our imaginary PCP box.

Build a tree from hashes

We need one more tool: a hash function \(H\) that turns an input into a short digest of \(\lambda\) bits. We assume it is hard for an efficient attacker to find two different inputs with the same digest; that property is called collision resistance. The security parameter \(\lambda\) controls the digest length.

Start with eight messages so we can see what happens. Hash each message to make eight leaves. Hash each pair of neighboring hashes to make four parents. Repeat: two grandparents, then one root \(c\). The root is our short commitment to all eight messages.

Now suppose the verifier asks for \(m_4\). We reveal \(m_4\), so it can calculate its leaf hash. To calculate that leaf's parent, the verifier only needs the neighboring leaf hash, not all the leaves. To go one level higher it needs the neighboring subtree hash. One sibling hash at each level is enough to reconstruct the root.

Which hashes must be opened?

Choose a message. Blue shows the path the verifier rebuilds; amber shows the sibling hashes it must receive.

Why is the opening short?

Suppose the tree has \(M=2^k\) leaves. The height is \(k\), because each level halves the number of hashes until one remains. The verifier needs exactly one sibling digest per level. Each digest has \(\lambda\) bits, so the opening uses \(k\lambda=\lambda\log_2 M\) bits of authentication hashes, in addition to the message and its index. The root itself has only \(\lambda\) bits.

Why can't the prover change the value?

Suppose two different messages at the same position both give the same committed root. If their leaf hashes are equal, we immediately have two different inputs with one hash output: a collision. If the leaf hashes differ, follow both proposed openings upward. Because they nevertheless end at the same root, at some parent two different child inputs must produce the same hash. That is also a collision.

Collision resistance says an efficient attacker cannot feasibly do this, so it cannot feasibly make two conflicting openings for one position.

We have proved the two properties we needed: one \(\lambda\)-bit root fixes a long list, and one position can be authenticated using only \(O(\lambda\log M)\) bits of path information. That's how cryptography gives the PCP verifier a practical substitute for its locked box. \(\square\)

Now the PCP verifier's ideal box can be replaced: a Merkle commitment fixes the bit string, and authentication paths answer its position queries. Let's combine the two mechanisms and check whether the resulting argument is actually short and sound.

Homework: three ways to commit to a list

We know what a vector commitment must do. This problem asks us to change its size in three different ways. Each time, the key question is the same: why can't one commitment be opened to two different values at the same index?

Let \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\) be a random oracle. We have \(M\) messages, each of \(|m|\) bits. The symbol \(\{0,1\}^{\ast}\) means any finite bit string.

HW1 · Problem 4(a)

Long commitment, no extra opening proof

Give a commitment of \(M\lambda\) bits whose opening requires \(O(1)\) extra bits. Prove position binding.

Show the solution

Put every message hash directly into the commitment:

\[c=(H(m_1),\ldots,H(m_M)).\]

To open position \(i\), reveal \(m_i\). The verifier hashes it and compares the result with the stored \(i\)-th hash. No additional authentication proof is needed.

Suppose both \(m_i\) and \(m_i'\ne m_i\) pass. They must satisfy \(H(m_i)=c_i=H(m_i')\). That's a collision in \(H\), which a polynomial-time adversary cannot feasibly find in the random-oracle model.

Thus the commitment is position binding. We saved opening size by paying for \(M\) hashes in the commitment. \(\square\)

HW1 · Problem 4(b)

Short commitment, reveal the whole list

Give a commitment of \(\lambda\) bits with an opening of \(O(M|m|)\) bits. Prove position binding.

Show the solution

Hash an unambiguous encoding of the entire ordered list:

\[c=H(\operatorname{Encode}(m_1,\ldots,m_M)).\]

To open index \(i\), send the entire list. The verifier recomputes its hash, checks it equals \(c\), and reads entry \(i\).

Could two different values at position \(i\) both work? Then two different encoded lists would have the same hash \(c\), another collision in \(H\).

The commitment is short and position binding, but each opening reveals the full list. This doesn't solve our succinct-proof problem. \(\square\)

HW1 · Problem 4(c)

Short commitment and short opening

Give a \(\lambda\)-bit commitment with an opening of \(O(\lambda\log M)\) bits. Prove position binding.

Show the solution

Use the Merkle tree from the previous lesson. The root is the \(\lambda\)-bit commitment. An opening gives the chosen message and one \(\lambda\)-bit sibling hash at each of the \(\log_2 M\) levels.

The verifier hashes upward to reconstruct the root. If two different messages at the same position reconstructed the same root, somewhere on the two paths different inputs would yield the same hash. This would break collision resistance.

So both size requirements and position binding hold. The tree combines the useful features of parts (a) and (b). \(\square\)

Put the PCP theorem and Merkle tree together

We now have exactly what we needed: a proof that can be checked by reading a few bits, and a way to authenticate those bits without sending the full proof. Does combining them actually give us cheap and reliable verification?

The PCP theorem supplies the test. The Merkle root makes all answers refer to one fixed proof string. Neither works alone: the PCP box was imaginary, while Merkle authentication tells us that a bit is unchanged, not that the whole statement is true. We need both.

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. A PCP test queries a constant \(k\) positions, chosen before seeing their answers, with perfect completeness and soundness error \(1/2\). Merkle commitments have \(\lambda\)-bit roots and openings of \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and communication polynomial in \(\lambda\) and \(\log n\).

Work through the construction and proof

First, the protocol

The prover computes its PCP proof string \(\pi\), builds a Merkle tree over the bits, and sends the root \(c\). This is message one. The root must be sent before the verifier chooses positions, or the prover could change the proof to suit the test.

The verifier chooses fresh randomness for \(\lambda\) independent PCP tests and sends all \(k\lambda\) requested positions together. That's message two. The prover returns the corresponding bits and their Merkle paths in message three.

The verifier checks both that every bit authenticates to root \(c\) and that every PCP test accepts. An authenticated bit is not necessarily a correct proof bit; the PCP predicates are still needed.

Verifier \(V\)

⟶

⟵

Does an honest proof pass?

Yes. A true statement has a PCP proof that passes every test. Every honest Merkle path also reconstructs the root. Thus the combined protocol has perfect completeness.

Can a false statement pass?

Assume the statement is false. After sending \(c\), a computationally bounded prover cannot change any authenticated bit except by breaking Merkle binding. So, apart from a negligible cryptographic failure, the verifier is testing one fixed PCP string.

For that fixed false proof, the PCP theorem bounds each independent test's acceptance by \(1/2\). All \(\lambda\) tests pass with probability at most \(2^{-\lambda}\). Adding the chance of breaking the Merkle commitment gives

\[\Pr[\text{false acceptance}]\le2^{-\lambda}+\operatorname{negl}(\lambda).\]

Here \(\operatorname{negl}(\lambda)\) denotes a probability that becomes smaller than the reciprocal of any fixed polynomial in \(\lambda\), for large enough \(\lambda\).

Have we kept communication short?

We send one root of \(\lambda\) bits. We authenticate \(k\lambda\) proof positions. Since \(k\) is constant and each path has \(O(\lambda\log M)\) bits, all paths together cost

\[O(k\lambda\cdot\lambda\log M)=O(\lambda^2\log M).\]

The PCP length is polynomial in \(n\), so \(\log M=O(\log n)\). The indices and opened bits do not change this leading bound. The entire communication is therefore \(O(\lambda^2\log n)\).

We have now proved the two things the question asked: negligible soundness error and succinct communication. Merkle binding makes the PCP tests apply to one fixed proof; the PCP theorem makes those few tests meaningful. \(\square\)

We have our first real construction: a succinct interactive argument. It has short communication and small soundness error. But the verifier still sends random queries, so it isn't non-interactive yet. We'll remove that message later with Fiat–Shamir.

Now notice something else. This construction checks an encoded proof bit by bit. For PLONK we want a different approach: put computation values into a polynomial and test algebraic equations about them. We already understand the principle of a fixed oracle; let's change what the oracle stores and what the verifier may ask it.

From checking proof bits to checking equations

The PCP construction is one route to a short proof: it checks a few carefully encoded bits. We now want to build a second route, which will lead to PLONK. Instead of asking about individual proof bits, can we ask whether a whole computation obeys an equation?

The essential rule remains the same: the prover first fixes the entire object stored in the box. The verifier then chooses its question, and the box must answer consistently with that fixed object. A protocol using such boxes is called an Interactive Oracle Proof, or IOP. An oracle is simply the name we give to the idealized box.

There are three interfaces in the lecture. You already know the first: the box stores a long bit string and reveals selected bits. For the next two, imagine that the proof is an ordered list of numbers, or a polynomial—a formula we can evaluate at a chosen number.

The box storesWhat the verifier asks
PCP: a fixed bit string \(\pi\)“What is bit \(i\)?” The box returns \(\pi_i\).
Linear IOP: a fixed list \((\pi_1,\ldots,\pi_M)\)“Multiply each entry by my chosen weight \(q_i\), then add them.” The box returns \(\sum_i q_i\pi_i\).
Polynomial IOP: a fixed polynomial \(f(X)\)“What does the formula give at \(X=z\)?” The box returns \(f(z)\).

A weight \(q_i\) is just a number selected by the verifier for list position \(i\). A polynomial like \(f(X)=X^2+1\) can be evaluated by substituting a number: for example, \(f(3)=10\). We'll develop the needed arithmetic carefully in the next chapter, using a number system called a field.

Why choose a polynomial box for PLONK? Because we can arrange the steps of a computation as values of one polynomial. Then the verifier can check equations about the steps by asking for the polynomial at just a few points. We'll prove why that works, rather than assuming it.

We will use the polynomial oracle. First we must show how one polynomial can hold many values. Then we need a reason why a false equation is unlikely to pass a random evaluation test. Both will come from elementary algebra over finite fields. This is the next step toward a PLONK proof, not a separate topic.
