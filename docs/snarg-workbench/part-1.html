I · Why SNARGs exist · Lecture §1

How can we check a computation without doing it again?

A server has done a million calculations and tells us the answer. We'd like to know if it's right. But checking every calculation would mean doing nearly the same amount of work ourselves.

Take the example in the notes. The server repeatedly applies SHA-256, a function that turns an input into a fixed-length string of bits. We give it an initial value \(x\). After a million applications, it gives us a final value \(y\).

What would convince us that \(y\) is correct? The server could send every intermediate value, and we could check that each is the SHA-256 hash of the one before it. That would work, but we'd have to perform a million checks. If the server sends only \(y\), we could recompute everything ourselves. That is no improvement either.

What we want is a proof that is much easier to check than the original computation.

What exactly are we trying to prove?

First separate two things. The statement \(x\) is what the verifier is being asked to believe. In the hash example it includes the starting value and the claimed final value. A witness \(w\) is extra information that establishes the claim, such as the list of intermediate hashes.

We write \(R(x,w)=1\) when a public checking procedure \(R\) decides that \(w\) is valid evidence for \(x\). The number \(1\) simply means “yes.” The set of statements with valid evidence is

\[L=\{x:\exists w,\;R(x,w)=1\}.\]

The symbol \(\exists\) means “there exists.” So \(x\) belongs to \(L\) precisely when at least one suitable witness exists. In cryptography, we'll often call \(L\) a language. It is just a set of valid statements.

We study statements where checking a given witness is efficient. These are the statements associated with the complexity class NP. Finding the witness may be difficult, even though checking it is straightforward.

Prover \(P\)

Knows the statement \(x\) and a witness \(w\). Builds a proof \(\pi\).

⟶
Verifier \(V\)

Knows \(x\), receives \(\pi\), and decides whether to accept.

Two things the proof must get right

If the statement is true and the prover follows the rules, the verifier should accept. We call this completeness. If the statement is false, a dishonest prover should almost never convince the verifier. We call this soundness.

The lecture asks for perfect completeness. It also allows a small probability \(\varepsilon\) of accepting a false statement:

\[ \begin{aligned} \Pr[\text{accept}\mid\text{true statement, honest prover}]&=1,\\ \Pr[\text{accept}\mid\text{false statement}]&\le\varepsilon. \end{aligned} \]

The symbol \(\Pr\) means probability; the random choices made during the proof determine the probabilities. In the second line, the dishonest prover can use any strategy allowed by the security model.

We now know what a proof must establish. But a proof could still be as long and expensive to check as the computation itself. We need a stronger requirement: the proof should be short.

A proof that is quicker to check

If I give you a million numbers as evidence, I haven't saved you much work. Can the proof remain small even when the computation gets enormous?

Call the proof \(\pi\), the public statement \(x\), and the witness \(w\). The vertical bars \(|\pi|\), \(|x|\), and \(|w|\) mean their lengths in bits. A standard NP proof can consist of the entire witness, so its length grows with \(|w|\).

A succinct proof should grow much more slowly. The notes use these bounds:

\[ |\pi|=O\bigl(\lambda,\operatorname{polylog}(|x|,|w|)\bigr) \] \[ T_V=O\bigl(\lambda,|x|,\operatorname{polylog}(|w|)\bigr). \]

Here \(T_V\) is the verifier's running time. The parameter \(\lambda\) controls the desired cryptographic security. The notation \(\operatorname{polylog}(n)\) means a fixed power of a logarithm, such as \((\log_2 n)^2\). And \(O(\cdot)\) describes how a quantity grows for large inputs; it is not an exact count of bytes or operations.

Why is the logarithm attractive? If the number of witness values doubles, its binary logarithm increases by just one. Move the slider and compare the two quantities. This is a comparison of growth rates, not a prediction of an actual SNARG's proof size.

The verifier is allowed time proportional to \(|x|\), since it may have to read the public statement. What we're trying to avoid is work proportional to the enormous private witness.

What does “non-interactive” add?

Sometimes the verifier sends a random question and the prover responds. That requires a conversation. For a non-interactive proof, the prover instead makes one proof string that anyone can check later, without asking the prover another question.

This gives the name SNARG: Succinct Non-Interactive Argument. The word argument signals that soundness is guaranteed against computationally bounded cheaters, relying on cryptography.

Notice that nothing we've said demands zero knowledge. A SNARG need not hide the witness. Zero knowledge is a further promise: the proof should not reveal private information beyond what the statement establishes. Nor is a proof of knowledge automatically guaranteed by the SNARG requirements.

There is still a difficulty. A proof may be very long, even if only a few parts are important. How could a verifier learn enough about it without reading it? A surprising theorem gives us a starting point.

Could three bits tell us whether a proof is wrong?

Suppose someone hands you an ordinary thousand-page calculation and asks you to check three random characters. You wouldn't expect to learn much. But what if the proof had been written in a very special way?

The PCP theorem says that, for any statement in NP, a prover can produce a specially encoded proof that a verifier checks by reading only three bits. The proof itself may be long. What is remarkable is the tiny number of bits the verifier needs to inspect.

The lecture states two guarantees. If the statement is true, there is an encoded proof that always passes. If it is false, every encoded proof the prover might supply has at most a \(1/2\) chance of passing the verifier's random test:

\[ \Pr[\text{accept}\mid\text{true statement, correct proof}]=1, \quad \Pr[\text{accept}\mid\text{false statement}]\le\tfrac12. \]

The theorem does not say that three bits of an ordinary witness are enough. The special encoding is essential. The lecture takes the theorem as a given; its long proof is not part of our course.

The box that makes the theorem work

Imagine that the prover puts the entire encoded proof \(\pi\) inside a locked box. The verifier can ask for bit \(i\), and the box returns \(\pi_i\). It cannot ask for the rest, and the prover cannot change the proof after seeing which bits are requested.

Prover

Writes the encoded proof \(\pi\) and locks it in the box.

⟶
Proof box

Remembers one fixed string and answers position queries.

⟷
Verifier

Chooses random positions and checks the returned bits.

The little bit-query simulator in this lesson shows how the box behaves; it does not attempt to simulate the PCP theorem itself.

If the proof has \(M\) bits, an index can be written with about \(\log_2 M\) bits. Thus the verifier needs only \(O(\log M)\) random bits to choose its positions, and receives a constant number of proof bits.

Can we make a false acceptance much less likely?

One test has error at most \(1/2\). Ask the box to pass \(t\) independent tests, all against the same fixed proof, and accept only if every test passes. Each new random test has conditional acceptance probability at most \(1/2\), so

\[\Pr[\text{all }t\text{ tests pass}]\le(1/2)^t=2^{-t}.\]

The independence is important: we choose fresh random questions for every test. The proof must remain fixed throughout. Use the slider to see why repeating a test makes a fixed false proof unlikely to pass them all.

How much does repetition help?

Move \(t\). The value shown is the proved upper bound for a fixed false proof, not a simulation of PCP encoding.

The locked box is imaginary. Sending the entire encoded proof to the verifier would ruin succinctness. Asking an uncommitted prover for individual bits would let the prover adapt the answers. We need a real way to fix a long string and then reveal just a few positions.

What is the proof box allowed to answer?

The important trick in the PCP example was not the physical box. It was that the prover had to fix its proof first, and the verifier could request only certain kinds of information from it.

We call this idea an Interactive Oracle Proof, or IOP. An oracle is simply our name for the trusted box that stores the prover's fixed information and answers the allowed queries. At this stage we're studying the mathematics, assuming the box behaves honestly. Later cryptography will replace that assumption.

Different types of IOPs allow different questions:

TypeWhat the prover fixesWhat the verifier asks
PCPA bit string \(\pi\)“What is bit \(i\)?” Answer: \(\pi_i\).
Linear IOPA vector \(\boldsymbol\pi\)“What is \(\sum_i q_i\pi_i\)?” The \(q_i\) values specify a weighted sum.
Polynomial IOPA polynomial \(\pi(X)\)“What is its value at \(z\)?” Answer: \(\pi(z)\).

A vector is just an ordered list of numbers. In a linear IOP the verifier chooses weights \(q_i\), multiplies each by the corresponding list entry \(\pi_i\), and adds the products. In a polynomial IOP the verifier chooses one number \(z\) and asks the polynomial to be evaluated there.

Why would we want the polynomial version? Because a polynomial can be arranged to represent a whole computation, and there are mathematical rules that let us test it at only a few points. That's the idea behind PLONK.

But first return to the simpler bit box. If we can make it real, we'll already have a way to build a SNARG from the PCP theorem.

What we need from cryptography is quite specific: a short value that fixes a long list, together with a small proof for any one list entry. That's a vector commitment.

How do you lock a million bits with one small value?

We want the prover to fix a whole list of proof bits, then let us inspect any chosen position. The proof for one position should be small. And the prover must not be able to change its answer later.

Suppose our list is \(m_1,\ldots,m_M\). A vector commitment makes a short value \(c\) that commits to the entire list. To reveal the value at position \(i\), the prover sends \(m_i\) and an opening proof that the verifier checks against \(c\).

What stops cheating? The property called position binding. Once the commitment is fixed, the prover must not be able to make two different values \(m_i\ne m'_i\) both look valid at the same position \(i\).

Build a tree of hashes

Take a hash function \(H\) with \(\lambda\)-bit outputs. Hash each message. Pair the hashes and hash each pair. Continue until one hash remains at the top. That final hash, called the root, is the commitment \(c\).

Why a tree? Suppose you want to open only \(m_4\). The verifier already knows \(H(m_4)\) once you reveal \(m_4\). To compute the parent hash, it needs only the hash of \(m_4\)'s sibling. To compute the next parent, it needs one hash for the next sibling subtree. One hash at each level is enough.

Open one message without revealing the rest

Choose the message. The blue nodes are the hashes the verifier reconstructs; the amber nodes are the sibling hashes it needs to receive.

How long is an opening?

For simplicity, let \(M=2^k\). A tree with \(M\) leaves has \(k\) levels from leaf to root. We just saw that we need one sibling hash per level. Therefore an opening uses \(k=\log_2M\) sibling hashes, each of \(\lambda\) bits:

\[\text{authentication-path length}=\lambda\log_2M\text{ bits}.\]

The commitment itself is just the root, so it has \(\lambda\) bits. We count the opened message and its index separately.

Why can't the prover change a message?

Suppose two different messages at the same leaf both lead to the same committed root. Follow their two hash calculations upward. At the first point where different child inputs produce the same hash, we've found a collision in \(H\): two different inputs with the same output.

Our cryptographic assumption says a computationally bounded adversary cannot feasibly find such a collision. Hence it cannot feasibly open one position to two different messages.

That is exactly position binding. The root fixes the list, and a logarithmic-length path lets us check any selected entry. This is the “locked box” behavior the PCP construction needs. \(\square\)

Homework: three ways to commit to a list

We know what a vector commitment must do. This problem asks us to change its size in three different ways. Each time, the key question is the same: why can't one commitment be opened to two different values at the same index?

Let \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\) be a random oracle. We have \(M\) messages, each of \(|m|\) bits. The symbol \(\{0,1\}^{\ast}\) means any finite bit string.

HW1 · Problem 4(a)

Long commitment, no extra opening proof

Give a commitment of \(M\lambda\) bits whose opening requires \(O(1)\) extra bits. Prove position binding.

Show the solution

Put every message hash directly into the commitment:

\[c=(H(m_1),\ldots,H(m_M)).\]

To open position \(i\), reveal \(m_i\). The verifier hashes it and compares the result with the stored \(i\)-th hash. No additional authentication proof is needed.

Suppose both \(m_i\) and \(m_i'\ne m_i\) pass. They must satisfy \(H(m_i)=c_i=H(m_i')\). That's a collision in \(H\), which a polynomial-time adversary cannot feasibly find in the random-oracle model.

Thus the commitment is position binding. We saved opening size by paying for \(M\) hashes in the commitment. \(\square\)

HW1 · Problem 4(b)

Short commitment, reveal the whole list

Give a commitment of \(\lambda\) bits with an opening of \(O(M|m|)\) bits. Prove position binding.

Show the solution

Hash an unambiguous encoding of the entire ordered list:

\[c=H(\operatorname{Encode}(m_1,\ldots,m_M)).\]

To open index \(i\), send the entire list. The verifier recomputes its hash, checks it equals \(c\), and reads entry \(i\).

Could two different values at position \(i\) both work? Then two different encoded lists would have the same hash \(c\), another collision in \(H\).

The commitment is short and position binding, but each opening reveals the full list. This doesn't solve our succinct-proof problem. \(\square\)

HW1 · Problem 4(c)

Short commitment and short opening

Give a \(\lambda\)-bit commitment with an opening of \(O(\lambda\log M)\) bits. Prove position binding.

Show the solution

Use the Merkle tree from the previous lesson. The root is the \(\lambda\)-bit commitment. An opening gives the chosen message and one \(\lambda\)-bit sibling hash at each of the \(\log_2 M\) levels.

The verifier hashes upward to reconstruct the root. If two different messages at the same position reconstructed the same root, somewhere on the two paths different inputs would yield the same hash. This would break collision resistance.

So both size requirements and position binding hold. The tree combines the useful features of parts (a) and (b). \(\square\)

Homework: make the PCP box real

We have two useful pieces. The PCP verifier needs to read only a few proof bits. A Merkle tree lets us authenticate a few bits from a fixed string. Put them together and we should get a short argument—but we must prove that the pieces really fit.

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. A PCP test queries a constant \(k\) positions, chosen before seeing their answers, with perfect completeness and soundness error \(1/2\). Merkle commitments have \(\lambda\)-bit roots and openings of \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and communication polynomial in \(\lambda\) and \(\log n\).

Work through the construction and proof

First, the protocol

The prover computes its PCP proof string \(\pi\), builds a Merkle tree over the bits, and sends the root \(c\). This is message one. The root must be sent before the verifier chooses positions, or the prover could change the proof to suit the test.

The verifier chooses fresh randomness for \(\lambda\) independent PCP tests and sends all \(k\lambda\) requested positions together. That's message two. The prover returns the corresponding bits and their Merkle paths in message three.

The verifier checks both that every bit authenticates to root \(c\) and that every PCP test accepts. An authenticated bit is not necessarily a correct proof bit; the PCP predicates are still needed.

Prover \(P\)
⟶
Verifier \(V\)
Send root \(c\)
⟶
Store the fixed commitment
Retain the proof and tree
⟵
Send all test positions
Return bits + Merkle paths
⟶
Check paths and PCP tests

Does an honest proof pass?

Yes. A true statement has a PCP proof that passes every test. Every honest Merkle path also reconstructs the root. Thus the combined protocol has perfect completeness.

Can a false statement pass?

Assume the statement is false. After sending \(c\), a computationally bounded prover cannot change any authenticated bit except by breaking Merkle binding. So, apart from a negligible cryptographic failure, the verifier is testing one fixed PCP string.

For that fixed false proof, the PCP theorem bounds each independent test's acceptance by \(1/2\). All \(\lambda\) tests pass with probability at most \(2^{-\lambda}\). Adding the chance of breaking the Merkle commitment gives

\[\Pr[\text{false acceptance}]\le2^{-\lambda}+\operatorname{negl}(\lambda).\]

Here \(\operatorname{negl}(\lambda)\) denotes a probability that becomes smaller than the reciprocal of any fixed polynomial in \(\lambda\), for large enough \(\lambda\).

Have we kept communication short?

We send one root of \(\lambda\) bits. We authenticate \(k\lambda\) proof positions. Since \(k\) is constant and each path has \(O(\lambda\log M)\) bits, all paths together cost

\[O(k\lambda\cdot\lambda\log M)=O(\lambda^2\log M).\]

The PCP length is polynomial in \(n\), so \(\log M=O(\log n)\). The indices and opened bits do not change this leading bound. The entire communication is therefore \(O(\lambda^2\log n)\).

We have now proved the two things the question asked: negligible soundness error and succinct communication. Merkle binding makes the PCP tests apply to one fixed proof; the PCP theorem makes those few tests meaningful. \(\square\)

This protocol still has three messages: the commitment, the random queries, and the openings. Once we understand how a hash can replace the verifier's random challenge, we'll make it non-interactive in HW3 4(b).
