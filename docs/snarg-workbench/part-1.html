What would count as convincing evidence?

Question. A server claims to have completed an expensive computation. What must the client check to know the claimed result is correct, without doing the computation again?

Suppose the public input is a value \(x\). The server applies SHA-256 a million times and returns an alleged result \(y\). An obvious verification method is to ask the server for every intermediate hash, then check each transition. This works, but the client performs approximately a million hash operations. Another is to request only \(y\) and recompute the whole chain. Neither achieves inexpensive verification.

To formulate exactly what should be proved, collect everything the verifier already knows into the statement \(x\), and call the extra evidence known to the prover the witness \(w\). A public relation \(R(x,w)\) is a procedure that checks this evidence. We choose the convention that \(R(x,w)=1\) means the evidence is valid.

\[\displaystyle L=\{x:\exists\,w\text{ such that }R(x,w)=1\}.\]

The symbol \(\exists\) means “there exists”; \(L\) is the set of statements for which at least one valid witness exists. For the hash-chain claim, let the statement contain the initial input and claimed final hash; the witness can contain all intermediate hashes. The relation checks the starting value, every transition, and the last value.

The reason for this formulation is that finding or constructing \(w\) may be expensive even when checking a proposed \(w\) is efficient. This is the central kind of statement studied in NP. Here, “efficient” means that the checking time grows at most as a polynomial in the input length. We do not need to assume that finding \(w\) itself is efficient.

Prover \(P\)

Knows \(x,w\); produces a proof \(\pi\).

⟶
Verifier \(V\)

Knows \(x\); checks \(\pi\) without receiving \(w\).

The mathematical goal is not to recover the witness. It is to decide reliably whether the public statement admits a witness.

The two ways verification can go wrong

If \(x\in L\), an honest prover holding a valid witness should be accepted. This property is completeness. The notes use perfect completeness: honest proofs are accepted with probability \(1\).

If \(x\notin L\), then no valid witness exists. A cheating prover must not be able to persuade the verifier except with a small soundness error \(\varepsilon\). In symbols, the two guarantees are

\[\Pr[V(x,\pi)=1\mid x\in L,\ \pi\leftarrow P(x,w)]=1,\qquad \Pr[V(x,\pi)=1\mid x\notin L]\le\varepsilon.\]

In the second probability the verifier's randomness is included and the cheating prover may use an arbitrary permitted strategy. “Argument” denotes a system whose soundness is guaranteed only against computationally bounded adversaries, typically through cryptographic assumptions.

What we established. A convincing proof must make true claims pass and false claims fail, while saving the verifier work compared with checking the whole witness. The next problem is to specify what “saving work” actually requires.

How short is succinct?

Question. Sending the complete witness is already a non-interactive proof. Why is it not a SNARG?

Let \(|x|\), \(|w|\), and \(|\pi|\) denote the lengths of the statement, witness and proof. Let \(\lambda\) be the security parameter: increasing it is intended to make successful computational attacks less likely. A conventional NP proof may simply send \(w\), making its length \(|w|\).

We want the cost of proof verification to grow very slowly with the witness size. The lecture adopts the following two requirements:

\[|\pi|=O\!\left(\lambda,\operatorname{polylog}(|x|,|w|)\right),\qquad T_V=O\!\left(\lambda,|x|,\operatorname{polylog}(|w|)\right).\]

Here, \(\operatorname{polylog}(n)\) means a fixed polynomial in \(\log n\), such as \((\log n)^2\). The big-\(O\) notation suppresses constant factors and describes asymptotic growth, not an exact number of bytes or processor instructions. The first condition keeps the proof short; the second keeps verification efficient. Reading the entire public statement \(x\) can require \(\Theta(|x|)\) time, so this dependence is permitted.

The proof must also be non-interactive: after the prover prepares \(\pi\), anyone with the statement and public verification information can check it without having to issue a fresh challenge to that prover.

Three distinct requirements
Succinctness
Short proof and inexpensive verification.
Non-interactivity
A transferable proof string, not an ongoing conversation.
Soundness
A false statement is accepted only with small probability.
Zero-knowledge (optional here)
Verification does not reveal the witness beyond the allowed information.

The resulting system is a SNARG: a Succinct Non-Interactive Argument. A SNARK adds a knowledge/extraction property; a zkSNARK also provides zero-knowledge. These are different guarantees and should not be inferred from the acronym “SNARG” alone.

What follows. We must now find a method that checks the consistency of a long proof using only a tiny amount of the proof. A major theorem says this is possible—but initially only in a special model of access.

Why three proof bits can be enough

Question. How can a verifier detect false statements after inspecting only three bits of a proof?

Ordinary witnesses do not have this property: three randomly chosen positions in an unstructured witness often reveal nothing relevant. The PCP theorem establishes that every NP statement has a specially encoded proof \(\pi\), of polynomial length, that permits a verifier to decide with only three bit queries (in the formulation quoted by the course).

Imagine placing this encoded proof in a sealed box. The prover must fix the complete string before the verifier chooses query positions. The box reveals the bits at the requested indices and nothing else. The verifier uses \(O(\log M)\) random bits to index an \(M\)-bit proof and receives only \(O(1)\) bits.

Prover

Encode proof \(\pi\) and seal all \(M\) bits.

⟶
Oracle box

Fixed bit string; responds only to index queries.

⟷
Verifier

Random positions, then a local predicate on returned bits.

For a true statement, the honest encoded proof always passes. For a false statement, every fixed encoded proof has acceptance probability at most \(1/2\). The quantifier “every” matters: soundness covers arbitrary fake strings, not only malformed honest proofs.

\[\Pr[V^\pi(x)=1\mid x\notin L]\le\tfrac12,\qquad \Pr[V^\pi(x)=1\mid x\in L,\ \pi\text{ honest}]=1.\]

The superscript \(V^\pi\) means that the verifier can query the fixed proof oracle \(\pi\). The theorem is an assumed result in these lecture notes; proving the PCP theorem itself is not part of the material.

Repeating the test

A soundness error of \(1/2\) is not small enough for cryptographic security. We can perform \(t\) independent PCP tests against the same fixed proof string and accept only if all pass. For every fixed false proof, each fresh test has acceptance probability at most \(1/2\). Therefore

\[\Pr[\text{all }t\text{ tests accept}]\le (1/2)^t=2^{-t}.\]
Test the soundness bound

Change the number of independent local PCP tests. The display reports the bound derived above, not an arbitrary animation.

What the theorem achieves—and what it does not. It gives a locally checkable proof inside an ideal box. It does not tell us how to transmit such a box. Sending the full string loses succinctness; requesting bit values from an uncommitted prover permits adaptive cheating. The next step is to enforce fixed answers cryptographically.

Interactive oracle proofs

Question. What precisely do we assume about the imaginary proof box, and how can its interface change?

An Interactive Oracle Proof (IOP) is a protocol where the prover submits special encoded information to one or more oracles and the verifier asks only prescribed queries. The ideal oracle ties all answers to a single already-fixed encoding. Security is proved first in this restricted, information-theoretic setting.

The interface matters because it determines which cryptographic commitment will eventually implement the oracle:

Oracle typeWhat is fixed?Allowed query and answer
PCPA bit string \(\pi\)Position \(i\); answer \(\pi_i\).
Linear IOPVector \(\boldsymbol\pi\in\mathbb F^M\)Vector \(\mathbf q\); answer \(\langle\mathbf q,\boldsymbol\pi\rangle=\sum_iq_i\pi_i\).
Polynomial IOPA polynomial \(\pi(X)\in\mathbb F[X]\)Point \(z\in\mathbb F\); answer \(\pi(z)\).

The field \(\mathbb F\) is a collection of numbers supporting addition, multiplication and division by nonzero elements. We will construct examples in finite fields later. The vector inner product is simply a sum of coordinate-wise products; it is the linear IOP's permitted operation.

PLONK will use the polynomial interface because a polynomial can encode many computation values and its algebraic identities can be checked by a few random evaluations. Before developing it, we finish the PCP construction by learning how to fix a vector of bits.

The useful abstraction. An IOP specifies exactly what the verifier may read; a commitment scheme will make those restrictions enforceable in an ordinary protocol. This is the two-stage blueprint used throughout the lecture.

One commitment for an entire vector

Question. Can the prover fix millions of proof bits while sending only a short digest, then authenticate any few positions?

A vector commitment has a commitment algorithm and an opening algorithm. Committing to \((m_1,\ldots,m_M)\) produces a digest \(c\). Later, an opening of position \(i\) provides \(m_i\) and a short proof that this value is consistent with \(c\).

We need position binding: no computationally bounded prover should be able to produce a commitment \(c\), one index \(i\), two different messages \(m_i\ne m'_i\), and two valid openings to them. This is exactly the “cannot change a bit after seeing the verifier's position” property required by the PCP box.

The Merkle construction

Let \(H\) be a collision-resistant hash function producing \(\lambda\)-bit outputs. Hash each message at a leaf, hash the concatenation of each pair of children at their parent, and continue to one root \(c\). Each parent value commits to the complete subtree below it.

Authentication-path explorer

Blue is the path reconstructed by the verifier; amber nodes are precisely the sibling hashes the prover must transmit.

Why does an opening need only \(\log_2 M\) sibling hashes?

Assume for simplicity that \(M=2^k\). The tree has \(k\) levels between each leaf and the root. The verifier starts with \(H(m_i)\). At the first level, one sibling hash is enough to reconstruct the parent hash; at the second, one more sibling hash reconstructs the grandparent; and so forth. After \(k\) such steps the verifier obtains a candidate root.

Thus the opening contains exactly \(k=\log_2M\) sibling hashes, plus the message and its position. The root commitment itself contains only \(\lambda\) bits. If each sibling is a \(\lambda\)-bit hash, the authentication hashes total \(O(\lambda\log M)\) bits.

Binding. Suppose two different messages at the same leaf both authenticate to the same root. Trace the two hash computations upward. At some level, different child inputs must yield an equal parent hash; otherwise distinct leaf hashes would produce different roots at every level. That would be a collision in \(H\) (including the possibility of a collision at the leaf itself).

Therefore a Merkle root fixes each position, except with the negligible probability of finding a hash collision, while the opening is logarithmic rather than linear in the vector length. This supplies the cryptographic operation that the PCP box lacked. \(\square\)

Homework 1: vector commitments

Exam skill. Choose a construction with the required commitment/opening sizes, then prove position binding with an explicit collision argument.

We are given a random oracle \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\), and an ordered vector of \(M\) messages of length \(|m|\). Each part asks for a different trade-off between commitment length and opening length.

HW1 · Problem 4(a)

Large commitment, constant proof

Construct a commitment of \(M\lambda\) bits with an \(O(1)\)-bit opening proof, and justify position binding.

Work through the solution

Set \(c=(H(m_1),\ldots,H(m_M))\). To open position \(i\), reveal \(m_i\); no auxiliary proof bits are necessary. The verifier checks \(H(m_i)=c_i\).

If two distinct values \(m_i,m_i'\) were accepted at the same position, then \(H(m_i)=c_i=H(m_i')\) would be a hash collision. Under the random-oracle assumption, a polynomial-time adversary finds such a collision only with negligible probability.

The verifier needs no separate authentication path because the commitment already contains the expected hash at every index. The price is that the commitment grows linearly with \(M\). \(\square\)

HW1 · Problem 4(b)

Short commitment, full-vector opening

Construct a \(\lambda\)-bit commitment with an \(O(M|m|)\)-bit opening proof, and justify position binding.

Work through the solution

Let \(c=H(\operatorname{enc}(m_1,\ldots,m_M))\), using an unambiguous encoding of the ordered list. To open position \(i\), reveal the entire ordered vector. The verifier recomputes its hash and reads its \(i\)-th entry.

If two different messages at position \(i\) could be opened under the same digest, the two complete vector encodings would be different yet have the same hash. That is a collision.

The root-sized commitment is short, but checking one position requires revealing and authenticating the whole vector. Hence this construction does not implement the succinct PCP box. \(\square\)

HW1 · Problem 4(c)

Short commitment and logarithmic opening

Construct a \(\lambda\)-bit commitment with an \(O(\lambda\log M)\)-bit opening proof, and prove position binding.

Work through the solution

Build the binary Merkle tree defined in the previous lesson and send the root. The opening consists of the message, its index, and the sibling hashes on the leaf-to-root path. Recompute each parent hash in the correct left/right order and compare the final value to the root.

The proof contains one \(\lambda\)-bit sibling value at each of \(\log_2M\) levels. If distinct messages could both authenticate at the same leaf, at least one equal parent hash would have different inputs, giving a collision in \(H\).

Both sizes meet the requirement: one \(\lambda\)-bit root and \(O(\lambda\log M)\) auxiliary proof bits, with position binding derived from collision resistance. \(\square\)

Homework 3: turning a PCP into an argument

Question. How do we combine the fixed-proof guarantee of a Merkle tree with the local soundness guarantee of a PCP so that the entire communication becomes succinct?

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. The verifier asks a constant \(k\) positions, selected before their answers are seen, and has perfect completeness and soundness error \(1/2\). A Merkle root has \(\lambda\) bits and each opening requires \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and total communication polynomial in \(\lambda,\log n\).

Full solution · protocol, correctness, soundness, communication

Construction

The prover first computes the PCP string \(\pi\) and commits to its complete vector of bits with a Merkle root \(c\). The prover retains the tree needed to authenticate openings. Its first message is \(c\). The verifier then chooses independent randomness for \(\lambda\) PCP tests and sends the resulting batch of \(k\lambda\) positions. This is a single second message, since none of the positions depends on previously revealed proof bits. The prover's third message contains every requested bit and its Merkle authentication path.

Prover \(P\)
⟶
Verifier \(V\)
Commit the fixed PCP \(\pi\): send root \(c\)
⟶
Store \(c\)
Retain \(\pi\) and the Merkle tree
⟵
All \(k\lambda\) queried positions
Return opened bits and paths
⟶
Verify paths and every PCP test

Completeness

If \(x\in L\), the PCP theorem supplies an encoded proof for which every PCP local predicate accepts. Correct Merkle paths also verify, so the combined verifier always accepts. This proves perfect completeness.

Soundness

Now assume \(x\notin L\). Once the root has been sent, position binding prevents an efficient prover from changing the answer at a fixed index without finding a hash collision. Except for negligible cryptographic failure, the openings must therefore act as responses from one fixed proof string. For any such false-proof string, each independent PCP test accepts with probability at most \(1/2\). Requiring all \(\lambda\) tests to accept gives

\[\Pr[\mathrm{accept}\mid x\notin L]\le 2^{-\lambda}+\operatorname{negl}(\lambda).\]

The first term comes from the PCP test; the second covers failure of Merkle binding. Without binding, the argument would be invalid: the prover could pick answers adaptively after seeing the requested positions.

Communication

The root costs \(\lambda\) bits. There are \(k\lambda=O(\lambda)\) openings because \(k\) is constant. Their total authentication-path size is

\[O(\lambda)\cdot O(\lambda\log M)=O(\lambda^2\log M).\]

Since \(M\) is a polynomial in \(n\), we have \(\log M=O(\log n)\). The requested indices add \(O(\lambda\log M)\) bits; the returned proof-bit values add \(O(\lambda)\). Thus the total communication is \(O(\lambda^2\log n)\), which is polynomial in \(\lambda,\log n\).

Both requirements are met: the encoded PCP supplies short probabilistic tests, while Merkle binding makes their answers refer to one fixed string; together they give negligible soundness error and succinct communication in three messages. This is an argument because binding is computational. \(\square\)

The remaining step, HW3 4(b), is to remove the verifier's challenge message. We will return to it after deriving Fiat–Shamir and its security conditions.
