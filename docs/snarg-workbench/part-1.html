Lecture §1 · SNARGs

How can we trust a calculation without repeating it?

A server claims to have applied SHA-256 a million times. The final hash is short, but checking it by repeating the computation takes a million steps. We want a proof that lets the verifier trust the result without doing that work.

What could the server send to convince you? An obvious suggestion is the entire chain of intermediate hashes. You could check that the first comes from your starting value, every subsequent hash comes from the previous one, and the last is the claimed result. That would settle the matter. But it makes you perform nearly a million checks.

The problem isn't that the server's result is difficult to state. Its final hash is short. The problem is that the evidence needed to trust it seems to require following the entire computation again.

Separate the claim from the evidence

There are two different objects here. The public statement describes what we're supposed to believe: the starting value, the rule “apply SHA-256 a million times,” and the claimed final hash. Call the whole public statement \(x\). The witness \(w\) is the extra evidence the server possesses—in our example, the intermediate hashes.

Given both \(x\) and \(w\), we can run an ordinary checking procedure \(R\). It returns \(R(x,w)=1\) when the evidence makes the claim valid, and 0 otherwise. This lets us write the set of true statements as

\[L=\{x:\text{there exists a }w\text{ with }R(x,w)=1\}.\]

That set is called a language. The symbol \(L\) is not a new computation—it's just the collection of all public statements for which suitable evidence exists. In complexity theory, NP covers problems whose YES statements have polynomial-length evidence that a deterministic checker can verify in polynomial time. We need no more complexity theory than that right now.

Now name the two parties. The prover \(P\) knows the witness and wants to convince the verifier \(V\), who knows the public statement. We want to replace the long witness by a new, much shorter proof \(\pi\), pronounced “pi.” We haven't built it yet. We are simply saying what we wish existed.

Prover \(P\)

Knows the public claim \(x\) and the long evidence \(w\).

⟶ short proof \(\pi\) ⟶
Verifier \(V\)

Checks \(x\) using the short proof, not the entire computation.

What would make such a proof trustworthy?

There are two opposite ways a proof system could fail. It might reject a correct calculation, or it might accept an invented result. We must exclude both.

Completeness means a true statement with an honest prover is accepted; the lecture requires this with probability 1. Soundness means that for a false statement, even a cheating prover should almost never make the verifier accept. Call that small error probability \(\varepsilon\).

\[ \Pr[\text{accept}\mid\text{honest proof of a true claim}]=1,\qquad \Pr[\text{accept}\mid\text{false claim}]\le\varepsilon. \]

A proof that merely looks convincing isn't enough. We must eventually justify why a cheating prover cannot satisfy its checks. And even a mathematically convincing proof isn't helpful here if checking it means running the original million steps.

So there are two demands, not one: the proof must be trustworthy, and it must be cheap to check. The next lesson makes “cheap” precise. Only after we know the cost we are trying to avoid can we sensibly ask how to construct such a proof.

Lecture §1 · Succinctness and non-interactivity

What does a genuinely short proof save us?

The server could send every intermediate hash. That would make the claim easy to check, but the verifier would still process a million steps. We therefore need two savings: a short proof and a fast check. Succinctness makes those requirements precise.

Let's measure the two kinds of evidence. The witness \(w\) is the long list of intermediate results. Its length in bits is written \(|w|\). The proposed new proof is \(\pi\), with length \(|\pi|\). These vertical bars mean size, not absolute value. If the witness contains one million 256-bit hashes, then \(|w|\) is roughly 256 million bits. Sending all of them wouldn't be a succinct proof.

But how small could the verifier's work conceivably become? Suppose it somehow needed to inspect only one chosen part of a huge object. At least naming that part need not be expensive.

What counts as saving the verifier work?

There are two costs to avoid. If the prover sends all of the intermediate hashes, the communication grows with the number of computation steps. If the verifier recomputes each hash, the verification time grows with the number of steps. A short proof that still requires a million verification operations would not solve our problem, and neither would a fast verification algorithm that first downloads the entire witness.

So we need both a short proof and a fast verifier. The lecture expresses how small those costs must become using logarithms. A logarithm grows slowly: for example, the base-two logarithm of 1,024 is 10, because ten doublings produce 1,024. We are not yet claiming that a verifier can check a million-step calculation using ten operations. We are setting a target for how slowly its work should grow.

The lecture's precise definition

The lecture asks for two efficiency properties at once. First, the proof itself must be short. Second, verifying it must be quick. Call the public-statement length \(|x|\), the verifier's running time \(T_V\), and the cryptographic security parameter \(\lambda\). The desired bounds are

\[ |\pi|=O\!\left(\lambda,\operatorname{polylog}(|x|,|w|)\right), \qquad T_V=O\!\left(\lambda,|x|,\operatorname{polylog}(|w|)\right). \]

The term \(\operatorname{polylog}(n)\) means a fixed power of a logarithm, such as \((\log_2 n)^2\). The point of that bound is that making the computation much larger must not force the verifier to repeat a comparable amount of work. The \(O\) notation describes the general rate of growth rather than an exact running time or byte count. Notice the permitted linear term \(|x|\) in verification: the verifier may need to read the entire public claim. What it shouldn't have to read is the entire witness.

That is succinctness. It is a stronger requirement than merely saying the new proof “looks shorter” in a small example.

Why does the lecture also require non-interactivity?

Imagine a cryptocurrency transaction that must be checked by many people. If every verifier has to send fresh questions to the original prover and wait for answers, the proof cannot simply circulate as an independently checkable object. We want the prover to publish one string that anybody can verify later. That's what non-interactive means.

A proof system combining these two properties is called a SNARG: a Succinct Non-Interactive Argument. The word “argument” indicates computational soundness based on cryptographic assumptions. Zero knowledge—the promise not to reveal information about the witness—is a separate property, not part of this definition.

We have defined our goal without yet knowing how to reach it. A normal NP proof reveals the whole witness, and checking only a few ordinary computation steps is not obviously reliable. The first construction will test whether a verifier can read very little of a specially prepared proof and still catch a dishonest claim.

Lecture §2 · The PCP theorem and the box model

Why can checking a few bits ever work?

We want to verify a long computation without checking every step. We tried checking only a few randomly selected transitions from the original computation trace. That failed: a dishonest trace can contain just one incorrect transition, which a small sample will probably miss. The next idea is to change the evidence being checked, not merely sample the same evidence more often.

Why prepare a different proof?

The original witness is a list of intermediate computation values. It is useful for ordinary verification, but a false result might cause only one of its many local checks to fail. Suppose instead that the prover prepares a longer string of bits with extra structure. Its bits need not correspond one-to-one to computation steps. They can include information chosen so that a verifier's prescribed local checks are much more likely to detect an invalid claim.

We call the process of producing this specially structured string an encoding. Encoding does not mean encryption, and it does not necessarily shorten the witness. Here it means replacing ordinary evidence with a representation designed for a particular verification procedure. We do not yet know how to construct such an encoding. The next theorem tells us one exists.

What exactly does the PCP theorem guarantee?

The PCP theorem is a mathematical existence result about probabilistically checkable proofs. In the version stated by the lecture, for any YES statement in NP, there exists a suitable encoded proof that an honest verifier accepts with probability 1. For a NO statement, every possible encoded proof is accepted with probability at most \(1/2\).

Why “there exists” rather than “every encoded proof”? A true statement may have many possible bit strings that are nonsense. Completeness promises an honest prover can construct an accepting one; it does not say arbitrary strings must be accepted. Soundness is stronger in the opposite direction: for a false statement, no fixed string may make the randomized verifier accept with probability greater than \(1/2\).

The verifier reads three bits of the encoded proof per test in the lecture's stated version. Three is a constant because it does not grow with the size of the computation. “Constant number of bits” describes the general efficiency property; “three bits” specifies the particular theorem used here. These are not competing claims.

\[ \begin{aligned} \text{True statement:}&\quad \exists\pi\;\Pr[V^\pi\text{ accepts}]=1,\\ \text{False statement:}&\quad \forall\pi\;\Pr[V^\pi\text{ accepts}]\le\tfrac12. \end{aligned} \]

Here \(\pi\) is the fixed encoded bit string, \(V^\pi\) means the verifier can request bits of that string, and the probability is over the verifier's random choices. The symbols \(\exists\) and \(\forall\) mean “there exists” and “for every.” These two lines are the precise completeness and soundness guarantees we need.

How are the three positions chosen?

The verifier uses randomness to choose which local PCP test to perform. That test specifies the three bit positions to read and a rule for deciding whether their values pass. The positions are therefore random in the sense that they depend on the verifier's random choice, but they are not three arbitrary uniformly sampled positions from the original computation trace. They are chosen according to the PCP verification algorithm.

This distinction explains why the earlier sampling attempt failed without contradicting the theorem. Uniformly checking three ordinary computation transitions might miss a single bad step. The PCP theorem guarantees a different encoding and a corresponding randomized test whose acceptance probability is bounded for every false statement.

Why does the lecture put the proof in a box?

The theorem assumes that all queried bits come from one fixed string \(\pi\). Imagine asking the prover for three positions while letting it decide their values after seeing the questions. It might tailor its answers to pass that particular test. We would no longer be applying the theorem to one fixed proof.

So the lecture introduces an ideal proof box, also called an oracle. Before the verifier chooses a test, the prover puts the entire encoded string into the box. The box stores that string unchanged. Later, when the verifier requests position \(i\), the box returns the bit \(\pi_i\) at that position. “Oracle” here is simply the technical name for this ideal query interface; it is not another cryptographic assumption.

Prover

Fixes one encoded proof \(\pi\).

⟶
Proof oracle

⟷

The point of the box is now exact: it enforces the fixed-proof assumption required by PCP soundness. It does not make a false statement true or magically certify the bits. The randomized PCP test supplies the correctness guarantee.

What if one-half soundness error is too large?

Run the PCP test \(t\) times, each time with independent verifier randomness, against the same fixed proof. Accept only if every test passes. For a false statement, the chance of passing all tests is at most

\[\Pr[\text{all }t\text{ tests accept}]\le(1/2)^t=2^{-t}.\]

The independence matters: fresh random choices produce independent tests when the proof string remains fixed. Move the slider to see how the proven upper bound changes.

How much communication will the queries require?

We have established that only three bits are read per test. To turn the ideal box into a real protocol, the verifier must also tell the prover which positions to open. If the encoded proof contains \(M\) bits, a position number between 0 and \(M-1\) can be represented using \(\lceil\log_2M\rceil\) binary digits. For example, a proof with eight positions needs three address digits per queried position.

This is the first time we need the address length: it measures the communication required to request the PCP bits. It has nothing to do with why those bits detect a false claim. The theorem supplies that guarantee; the logarithm measures the cost of naming the queries.

Cost of specifying one query position

Here the number \(2^k\) represents the number of possible positions in an encoded proof, and \(k\) is the number of binary address digits. This figure measures addressing cost, not soundness.

We now have a mathematical solution to the original sampling problem: the PCP theorem provides a specially encoded proof that can be checked using only a few carefully chosen bits, with a proved error bound. But our proof box is imaginary. If the prover simply sends the full encoded string, communication is too large. If it answers queries without fixing the string, the soundness theorem no longer applies. The next lesson constructs a short commitment to one fixed string and authenticates the queried bits. That is why we need vector commitments and Merkle trees.

Lecture §2 · From PCPs to SNARGs

How can the prover lock the proof without sending it?

The PCP verifier asks for three bits of a proof that must already be fixed. The ideal proof box guarantees this, but a real prover could invent answers after seeing the questions. We need a short commitment that fixes every bit before the verifier asks for any of them.

Suppose the encoded PCP string has \(M\) bits. Think of it as a list \((m_1,\ldots,m_M)\), with one bit \(m_i\) at each position \(i\). A vector commitment creates a short public value \(c\) for that whole list. Later, to open position \(i\), the prover reveals \(m_i\) and some authentication data that the verifier checks against \(c\).

The critical rule is position binding: once \(c\) has been sent, a computationally bounded prover must not be able to open the same position \(i\) to two different bit values with valid proofs. If we had this, the verifier's random queries could no longer influence what the proof says at each position. The PCP soundness guarantee would become applicable to the answers it receives.

Build the commitment from hashes

A hash function \(H\) turns data into a short digest of \(\lambda\) bits. The security property we need is collision resistance: it should be infeasible to find two different inputs with the same digest. The parameter \(\lambda\) controls its security level.

Hash each message to make the leaves of a binary tree. Hash pairs of neighboring hashes to make their parents. Keep going until one hash remains at the top. That one value, the Merkle root \(c\), is the commitment to the whole list.

To open one message, the verifier already has the message and can hash it to get its leaf hash. It then needs only the neighboring hash to calculate that leaf's parent, one neighboring subtree hash for the next parent, and so on until the root. It compares the reconstructed root with the previously received \(c\).

Open one position from a fixed tree

Move the index. The blue nodes are the hashes the verifier reconstructs; the amber nodes are the neighboring hashes the prover supplies.

Why is this short—and why can we trust it?

If the tree has \(M=2^k\) leaves, it has \(k=\log_2M\) levels. We need one neighboring digest per level, and each digest has \(\lambda\) bits. So the authentication data for one opening is \(O(\lambda\log M)\) bits. The commitment itself is only a single \(\lambda\)-bit digest.

Where position binding comes from

Suppose a cheater manages to open the same leaf position as two different values under the same root \(c\). If the two leaf hashes are identical, it has found a hash collision. If they differ, follow the two authentication paths upward. At some stage different inputs must produce the same parent hash, since the paths ultimately reach the same root. That's also a collision.

So, assuming the hash is collision-resistant, a feasible dishonest prover cannot construct two conflicting valid openings to the same position.

A short Merkle root fixes the long encoded proof, and each requested bit can be authenticated by a logarithmic-length path. We have replaced the ideal PCP box with the specific cryptographic behavior it required. \(\square\)

I · Why SNARGs exist · HW1, Problem 4

Homework: three ways to commit to a list

We need to fix a long list before the verifier chooses which entry to inspect. A vector commitment does exactly that. This homework compares three ways to construct one and asks why the prover cannot later open the same position to different values.

Let \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\) be a random oracle. We have \(M\) messages, each of \(|m|\) bits. The symbol \(\{0,1\}^{\ast}\) means any finite bit string.

HW1 · Problem 4(a)

Long commitment, no extra opening proof

Give a commitment of \(M\lambda\) bits whose opening requires \(O(1)\) extra bits. Prove position binding.

Show the solution

Put every message hash directly into the commitment:

\[c=(H(m_1),\ldots,H(m_M)).\]

To open position \(i\), reveal \(m_i\). The verifier hashes it and compares the result with the stored \(i\)-th hash. No additional authentication proof is needed.

Suppose both \(m_i\) and \(m_i'\ne m_i\) pass. They must satisfy \(H(m_i)=c_i=H(m_i')\). That's a collision in \(H\), which a polynomial-time adversary cannot feasibly find in the random-oracle model.

Thus the commitment is position binding. We saved opening size by paying for \(M\) hashes in the commitment. \(\square\)

HW1 · Problem 4(b)

Short commitment, reveal the whole list

Give a commitment of \(\lambda\) bits with an opening of \(O(M|m|)\) bits. Prove position binding.

Show the solution

Hash an unambiguous encoding of the entire ordered list:

\[c=H(\operatorname{Encode}(m_1,\ldots,m_M)).\]

To open index \(i\), send the entire list. The verifier recomputes its hash, checks it equals \(c\), and reads entry \(i\).

Could two different values at position \(i\) both work? Then two different encoded lists would have the same hash \(c\), another collision in \(H\).

The commitment is short and position binding, but each opening reveals the full list. This doesn't solve our succinct-proof problem. \(\square\)

HW1 · Problem 4(c)

Short commitment and short opening

Give a \(\lambda\)-bit commitment with an opening of \(O(\lambda\log M)\) bits. Prove position binding.

Show the solution

Use the Merkle tree from the previous lesson. The root is the \(\lambda\)-bit commitment. An opening gives the chosen message and one \(\lambda\)-bit sibling hash at each of the \(\log_2 M\) levels.

The verifier hashes upward to reconstruct the root. If two different messages at the same position reconstructed the same root, somewhere on the two paths different inputs would yield the same hash. This would break collision resistance.

So both size requirements and position binding hold. The tree combines the useful features of parts (a) and (b). \(\square\)

I · Why SNARGs exist · HW3, Problem 4(a)

Put the PCP theorem and Merkle tree together

We have two ingredients: the PCP theorem supplies a meaningful three-bit test, and a Merkle commitment authenticates the answers against one fixed proof. This homework asks whether combining them really produces a protocol with low soundness error and short communication. We will calculate both rather than assume they follow.

The PCP theorem supplies the test. The Merkle root makes all answers refer to one fixed proof string. Neither works alone: the PCP box was imaginary, while Merkle authentication tells us that a bit is unchanged, not that the whole statement is true. We need both.

Follow the construction before proving it

There is no need to invent a complicated new protocol. Start with the question the PCP verifier would have asked its ideal box. The only change is that the prover must now prove that each answer belongs to the string it committed to.

First message: the prover constructs an encoded PCP proof, commits to its complete bit string using a Merkle tree, and sends the root \(c\). The verifier has received no proof bits yet. What the root accomplishes is to fix them before the questions are known.

Second message: the verifier chooses random PCP tests and sends their requested bit positions. It chooses these positions only after receiving \(c\). A false prover cannot know beforehand which bits it will have to open.

Third message: the prover returns the requested bits along with their Merkle authentication paths. The verifier checks the paths against \(c\), then applies the PCP test to the authenticated bits.

Why check both? An authenticated bit can be part of a completely false proof string. Merkle verifies consistency with the committed string; PCP supplies the rule that makes a false statement unlikely to pass. That is the division of labor behind the construction. The homework below asks you to prove the soundness and communication bounds formally.

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. A PCP test queries a constant \(k\) positions, chosen before seeing their answers, with perfect completeness and soundness error \(1/2\). Merkle commitments have \(\lambda\)-bit roots and openings of \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and communication polynomial in \(\lambda\) and \(\log n\).

Read the quantities before solving: \(n\) is the public statement length; \(M\) is the number of bits in the encoded PCP proof; “\(\operatorname{poly}(n)\)” means bounded by a fixed power of \(n\). In this problem \(k\) is the fixed number of positions read per PCP test (three in our lecture's version), not the number of address digits called \(k\) in the earlier logarithm example. Here \(\lambda\) is used as both the security parameter and the number of repetitions needed to drive the error down.

Work through the construction and proof

Choose enough tests to get negligible error

Use the three messages we just constructed. We now specify the number of tests: ask \(\lambda\) independent PCP tests, each involving \(k\) requested positions. If the same position appears several times it need only be opened once; counting \(k\lambda\) openings gives a simple valid upper bound.

Does an honest proof pass?

Yes. A true statement has a PCP proof that passes every test. Every honest Merkle path also reconstructs the root. Thus the combined protocol has perfect completeness.

Can a false statement pass?

Assume the statement is false. After sending \(c\), a computationally bounded prover cannot change any authenticated bit except by breaking Merkle binding. So, apart from a negligible cryptographic failure, the verifier is testing one fixed PCP string.

For that fixed false proof, the PCP theorem bounds each independent test's acceptance by \(1/2\). All \(\lambda\) tests pass with probability at most \(2^{-\lambda}\). Adding the chance of breaking the Merkle commitment gives

\[\Pr[\text{false acceptance}]\le2^{-\lambda}+\operatorname{negl}(\lambda).\]

Here \(\operatorname{negl}(\lambda)\) denotes a probability that becomes smaller than the reciprocal of any fixed polynomial in \(\lambda\), for large enough \(\lambda\).

Have we kept communication short?

We send one root of \(\lambda\) bits. We authenticate \(k\lambda\) proof positions. Since \(k\) is constant and each path has \(O(\lambda\log M)\) bits, all paths together cost

\[O(k\lambda\cdot\lambda\log M)=O(\lambda^2\log M).\]

Why can we replace \(\log M\) by \(O(\log n)\)? The PCP theorem gives a polynomial bound on \(M\). If \(M\le n^a\) for some fixed constant \(a\), taking logarithms gives \(\log M\le\log(n^a)=a\log n\). That is exactly what \(O(\log n)\) means. The query indices and opened bits don't change the leading asymptotic bound, so total communication is \(O(\lambda^2\log n)\).

We have now proved the two things the question asked: negligible soundness error and succinct communication. Merkle binding makes the PCP tests apply to one fixed proof; the PCP theorem makes those few tests meaningful. \(\square\)

We have our first real construction: a succinct interactive argument. It has short communication and small soundness error. But the verifier still sends random queries, so it isn't non-interactive yet. We'll remove that message later with Fiat–Shamir.

Now notice something else. This construction checks an encoded proof bit by bit. For PLONK we want a different approach: put computation values into a polynomial and test algebraic equations about them. We already understand the principle of a fixed oracle; let's change what the oracle stores and what the verifier may ask it.

Lecture §2.1 · Interactive Oracle Proofs

Why did we use an imaginary box first?

PCPs and Merkle trees give us one way to check a large computation. But the PCP encoding is expensive. We want to keep the useful part—the verifier asks only a few questions about fixed evidence—while choosing a representation better suited to arithmetic. That leads to interactive oracle proofs and, eventually, polynomial queries.

In the first stage, we pretend there is a trusted oracle, or proof box, storing one object supplied by the prover. It allows the verifier to ask only specific kinds of queries. We prove completeness and soundness in that ideal model, without cryptographic assumptions. This is called an Interactive Oracle Proof (IOP).

In the second stage, a cryptographic commitment replaces the oracle. The prover must commit to the object before seeing the verifier's query, and authentication stops it from changing answers later. After that, Fiat–Shamir can often remove the verifier's interactive challenge. We won't yet assume that this last step is automatically secure; we'll return to its conditions.

At this point we could stop with the PCP-and-Merkle construction: it demonstrates the blueprint, and the homework proves its communication and soundness bounds. But the lecture warns that this route is extremely inefficient for practical verification. PCPs require a complicated, potentially very long encoding of an arbitrary NP witness. We need the same fixed evidence, few queries principle in a form that exploits the structure of computations instead.

The computation we're trying to check consists of arithmetic steps. That suggests another representation: rather than encode arbitrary proof bits, store the intermediate numbers in a polynomial, then test the arithmetic relations among those numbers. The verifier's queries would return polynomial evaluations, not bit positions. We still need to prove such a test is sound; the oracle interface alone provides no guarantee.

Why might we want a different kind of box?

The PCP box stores bits and answers “what is the bit at position \(i\)?” But a long computation consists of numbers that satisfy equations. Perhaps it would be more natural if the box could answer questions about those numbers or equations directly.

The lecture describes three interfaces. We already know the first one:

IOP typeWhat the prover fixesWhat the verifier can ask
PCPA string \(\pi\) of bits.“What is bit \(i\)?” The oracle reveals \(\pi_i\).
Linear IOPA list \(\boldsymbol\pi=(\pi_1,\ldots,\pi_n)\) of field values.“Calculate the weighted sum \(\sum_i q_i\pi_i\),” where the verifier chooses weights \(q_i\).
Polynomial IOPA polynomial \(f(X)\) over a field.“What is \(f(z)\)?” The verifier chooses the point \(z\).

A linear combination is just a weighted sum: with values \((2,3,4)\) and weights \((1,0,2)\), the answer is \(1\cdot2+0\cdot3+2\cdot4=10\). A polynomial evaluation is just substitution: if \(f(X)=X^2+1\), asking at \(z=3\) gives \(f(3)=10\).

These interfaces all describe which questions are allowed. They do not themselves prove that an oracle-based protocol is sound. We still have to construct a meaningful verifier test and prove its security. The lecture briefly introduces linear IOPs because a later lecture uses them for aggregating private statistics; our present goal is the polynomial IOP used by PLONK.

The two constructions are alternative ways to exploit the same blueprint—not steps where a PCP is converted into a polynomial. We will now attempt the polynomial route on a concrete claim from the lecture: the value of the hundredth Fibonacci number. The immediate question will be how the prover can represent a sequence of 101 values in a polynomial. Only then will we ask what field arithmetic or polynomial identities we need to check it.
