Lecture §1 · SNARGs

How can somebody prove they did a calculation?

Imagine that a server takes an input and applies SHA-256 to it a million times. It tells you the final result. You could check the answer by doing the same million operations yourself—but then you haven't saved any work.

There is another obvious way. Ask the server to send all the intermediate hashes. Each one is the input to the next SHA-256 operation, so you could check each transition. That would be convincing. Unfortunately, it still means checking a million operations, and you also have to receive a million values.

Notice what makes this difficult. We aren't asking whether the answer looks plausible. We want to rule out a server that simply invents a result. Yet we don't want to repeat the very work we asked the server to do.

What are we being asked to believe?

Let's name the things already in our example. The statement, which we'll call \(x\), is the public claim: the starting input, the number of SHA-256 applications, and the claimed final result. It contains everything the client already knows.

The server can produce more evidence: the list of intermediate hashes. We'll call this list \(w\), the witness. If we had \(w\), we could check the computation step by step. Let \(R(x,w)=1\) mean “all those checks pass”; otherwise the checker returns 0.

For a general computational problem, a statement is true when some valid witness exists. We collect all true statements into a set called a language \(L\):

\[L=\{x:\exists w,\ R(x,w)=1\}.\]

The symbol \(\exists\) just means “there exists.” In words: \(x\) belongs to \(L\) if there is at least one witness making the ordinary checker accept. The class NP consists of problems of this kind when the witness is reasonably short and can be checked in polynomial time. Finding that witness may be difficult; checking one that is supplied must be efficient.

For now, the ordinary evidence \(w\) may still be enormous. That's the problem we're trying to solve, not a problem we've already solved by introducing notation.

What would a useful proof look like?

Call the server the prover \(P\), and the client the verifier \(V\). We'd like the prover to send a much shorter string \(\pi\), called a proof, instead of giving us the complete witness \(w\). The verifier would check \(\pi\) together with the public claim \(x\).

Prover \(P\)

Knows the public claim \(x\) and the long evidence \(w\).

⟶
Verifier \(V\)

Receives a proposed short proof \(\pi\) and decides whether to accept \(x\).

We have to insist on two promises. If the claim is true and the prover follows the protocol, the verifier should accept. This is completeness. If the claim is false, no cheating strategy should make the verifier accept except with a very small probability. This is soundness.

The lecture seeks perfect completeness—honest proofs always pass—and a small soundness error, which we'll call \(\varepsilon\):

\[\Pr[\text{accept}\mid\text{honest, true claim}]=1,\qquad \Pr[\text{accept}\mid\text{false claim}]\le\varepsilon.\]

Here \(\Pr\) denotes probability, and the second inequality must apply against all permitted dishonest provers. We do not know how to make such a short proof yet.

So the first question is very concrete: **how much smaller and easier to check must \(\pi\) be than the witness \(w\) before we can call this a real improvement?** The lecture answers that by defining succinctness.

Lecture §1 · Succinctness and non-interactivity

What would actually make the proof cheaper?

We don't want the server merely to repackage its million intermediate hashes. We need the amount of material the verifier reads—and the work it performs—to grow much more slowly than the calculation itself.

Let's measure sizes in bits. We write \(|w|\) for the number of bits in the ordinary witness and \(|\pi|\) for the number of bits in the proof we hope to construct. For example, a list of a million 256-bit hashes already contains about 256 million bits. If the “proof” were that entire list, the verifier would still have to process essentially all of it.

A small question about a large list

Imagine a list containing eight bits. To ask for bit number 5, we don't need to transmit the whole list. We can send the binary address \(101\), which means five. Three binary digits have \(2^3=8\) different possible combinations, enough to name every position from 0 to 7.

Now imagine the witness contains \(2^k\) bits, where \(k\) is simply the number of binary address digits. Each new digit doubles the number of positions we can address. Move the slider to see both quantities change together.

How many bits does it take to name a position?

The small number \(k\) is the address length. The larger number \(|w|=2^k\) is the size of the imaginary witness. This is not the size of a SNARG proof.

We express the relationship as \(\log_2(2^k)=k\). The logarithm answers: “How many doublings does it take to reach this number?” That's why logarithms are attractive when we work with enormous objects.

But a short address is not a short proof. Asking for a few bits from a long list is easy; deciding whether those few bits tell us anything about a million-step computation is the hard part. We'll have to solve that separately.

The lecture's actual requirement

Let \(|x|\) be the length in bits of the public statement, and \(T_V\) the verifier's running time. Let \(\lambda\) be a security parameter: larger \(\lambda\) is used to make successful attacks less likely. The lecture defines succinctness using the bounds

\[ |\pi|=O\bigl(\lambda,\operatorname{polylog}(|x|,|w|)\bigr), \qquad T_V=O\bigl(\lambda,|x|,\operatorname{polylog}(|w|)\bigr). \]

A polylogarithm is a fixed power of a logarithm, such as \((\log n)^2\). The big-\(O\) notation describes how cost scales as inputs become large; it does not give an exact number of bytes or milliseconds. The verifier is allowed time proportional to \(|x|\), because it must at least read the public claim. But it must not have to read the whole witness \(w\).

So “succinct” requires both a short proof and fast checking. Either one alone would be insufficient.

Why must it also be non-interactive?

In a protocol with interaction, the verifier sends the prover questions and waits for answers. Imagine verifying a cryptocurrency transaction: every person who wants to check it shouldn't have to contact the original prover. We would prefer one fixed proof string that anybody can inspect later. That's what non-interactive means.

Put the two properties together and we get a SNARG: a Succinct Non-Interactive Argument. “Argument” means the security relies on computational assumptions against efficient adversaries. A SNARG needn't be zero-knowledge: keeping the witness private is a separate property, which the lecture deliberately leaves aside at this stage.

We know exactly what we want now. But an ordinary NP proof reveals its witness, so it is usually not succinct. To see a possible way out, we'll first allow ourselves an imaginary verifier that can inspect only a few bits of a long encoded proof. Before using that idea, we must ask whether checking just a few bits could ever be convincing.

Lecture §2 · The PCP box experiment

Can a verifier learn enough from three proof bits?

We want to avoid reading a long witness. Let's try the most obvious shortcut: the prover sends the list of intermediate calculation values, and the verifier checks only three randomly chosen steps. Is that convincing?

Not in general. Suppose the server performs a million steps but changes only the final result. There can be almost a million correct transitions and just one false transition. If we sample only three of the transitions uniformly, the chance of finding that single bad one is tiny. The short question isn't the problem. The problem is that the evidence is written in a form where a single lie can hide among correct entries.

What if we could rewrite the evidence so that a false claim cannot hide in that way? That's the motivation for a probabilistically checkable proof, or PCP. We are not just sampling the original witness anymore. We first encode it into a specially structured proof string; the verifier then checks a few positions selected according to a carefully designed random test.

The theorem, and what it does not say

The PCP theorem says that for statements in NP, such an encoding exists. In the form cited by our lecture, a verifier can decide whether to accept by reading just three bits of a polynomial-length encoded proof. Honest proofs of true statements always pass; every fixed encoded proof for a false statement passes with probability at most one-half.

\[\Pr[\text{accept}\mid\text{true claim, honest proof}]=1,\qquad \Pr[\text{accept}\mid\text{false claim}]\le\tfrac12.\]

This is a deep theorem supplied by the lecture. We are not proving that encoding here, nor claiming that any three random bits of an ordinary witness are sufficient. The theorem's guarantee is precisely what makes the special encoding useful.

Let's call the encoded proof \(\pi_{\rm PCP}\), and let \(M\) denote its length in bits. An index into those \(M\) positions requires only \(O(\log M)\) bits to specify. The verifier receives three proof bits, but the encoded proof itself may be very long—even longer than the original witness.

What is the “box” actually doing?

Imagine the prover locks the entire \(\pi_{\rm PCP}\) string inside a box before the verifier chooses any queries. Later the verifier asks for positions \(i,j,k\); the box returns the bits already stored there. The prover cannot change the contents to suit the question.

Prover

Fixes the complete specially encoded proof \(\pi_{\rm PCP}\).

⟶
Locked proof box

Answers queries from the same unchanged string.

⟷
Verifier

Chooses a small number of positions and checks their values.

The fixed string is essential. Without it, a dishonest prover could see the requested positions and invent whichever answers make the verifier's test pass. The PCP theorem bounds the acceptance probability only when all answers come from one proof fixed before the test is chosen.

Can we reduce the one-half error?

Yes. Repeat the PCP test \(t\) times with fresh independent randomness, always against that same fixed encoded proof. Accept only if every test passes. For a false claim, each test passes with probability at most \(1/2\), so

\[\Pr[\text{all }t\text{ tests pass}]\le(1/2)^t=2^{-t}.\]
Repeat the test on one fixed encoded proof

Change \(t\) to see the theoretical soundness bound. This illustrates the PCP theorem's guarantee; it does not generate a real PCP encoding.

This is the first real breakthrough: mathematically, a few queries can test a long specially encoded proof. But the locked box is imaginary. If the prover simply sends the entire PCP proof, the proof won't be succinct; if we ask it for bits directly, it may change its answers. We need a cryptographic way to make a short commitment to the whole string and later authenticate only the few positions the verifier asks for.

Lecture §2 · From PCPs to SNARGs

How can the prover lock the proof without sending it?

The PCP verifier needs a few bits from one fixed long string. The missing tool must let the prover commit to the entire string using a short value, then convincingly reveal whichever individual positions the verifier asks for. This is a vector commitment.

Suppose the encoded PCP string has \(M\) bits. Think of it as a list \((m_1,\ldots,m_M)\), with one bit \(m_i\) at each position \(i\). A vector commitment creates a short public value \(c\) for that whole list. Later, to open position \(i\), the prover reveals \(m_i\) and some authentication data that the verifier checks against \(c\).

The critical rule is position binding: once \(c\) has been sent, a computationally bounded prover must not be able to open the same position \(i\) to two different bit values with valid proofs. This is exactly what the locked PCP box gave us for free.

Build the commitment from hashes

A hash function \(H\) turns data into a short digest of \(\lambda\) bits. The security property we need is collision resistance: it should be infeasible to find two different inputs with the same digest. The parameter \(\lambda\) controls its security level.

Hash each message to make the leaves of a binary tree. Hash pairs of neighboring hashes to make their parents. Keep going until one hash remains at the top. That one value, the Merkle root \(c\), is the commitment to the whole list.

To open one message, the verifier already has the message and can hash it to get its leaf hash. It then needs only the neighboring hash to calculate that leaf's parent, one neighboring subtree hash for the next parent, and so on until the root. It compares the reconstructed root with the previously received \(c\).

Open one position from a fixed tree

Move the index. The blue nodes are the hashes the verifier reconstructs; the amber nodes are the neighboring hashes the prover supplies.

Why is this short—and why can we trust it?

If the tree has \(M=2^k\) leaves, it has \(k=\log_2M\) levels. We need one neighboring digest per level, and each digest has \(\lambda\) bits. So the authentication data for one opening is \(O(\lambda\log M)\) bits. The commitment itself is only a single \(\lambda\)-bit digest.

Where position binding comes from

Suppose a cheater manages to open the same leaf position as two different values under the same root \(c\). If the two leaf hashes are identical, it has found a hash collision. If they differ, follow the two authentication paths upward. At some stage different inputs must produce the same parent hash, since the paths ultimately reach the same root. That's also a collision.

So, assuming the hash is collision-resistant, a feasible dishonest prover cannot construct two conflicting valid openings to the same position.

A short Merkle root fixes the long encoded proof, and each requested bit can be authenticated by a logarithmic-length path. We have replaced the ideal PCP box with the specific cryptographic behavior it required. \(\square\)

I · Why SNARGs exist · HW1, Problem 4

Homework: three ways to commit to a list

We know what a vector commitment must do. This problem asks us to change its size in three different ways. Each time, the key question is the same: why can't one commitment be opened to two different values at the same index?

Let \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\) be a random oracle. We have \(M\) messages, each of \(|m|\) bits. The symbol \(\{0,1\}^{\ast}\) means any finite bit string.

HW1 · Problem 4(a)

Long commitment, no extra opening proof

Give a commitment of \(M\lambda\) bits whose opening requires \(O(1)\) extra bits. Prove position binding.

Show the solution

Put every message hash directly into the commitment:

\[c=(H(m_1),\ldots,H(m_M)).\]

To open position \(i\), reveal \(m_i\). The verifier hashes it and compares the result with the stored \(i\)-th hash. No additional authentication proof is needed.

Suppose both \(m_i\) and \(m_i'\ne m_i\) pass. They must satisfy \(H(m_i)=c_i=H(m_i')\). That's a collision in \(H\), which a polynomial-time adversary cannot feasibly find in the random-oracle model.

Thus the commitment is position binding. We saved opening size by paying for \(M\) hashes in the commitment. \(\square\)

HW1 · Problem 4(b)

Short commitment, reveal the whole list

Give a commitment of \(\lambda\) bits with an opening of \(O(M|m|)\) bits. Prove position binding.

Show the solution

Hash an unambiguous encoding of the entire ordered list:

\[c=H(\operatorname{Encode}(m_1,\ldots,m_M)).\]

To open index \(i\), send the entire list. The verifier recomputes its hash, checks it equals \(c\), and reads entry \(i\).

Could two different values at position \(i\) both work? Then two different encoded lists would have the same hash \(c\), another collision in \(H\).

The commitment is short and position binding, but each opening reveals the full list. This doesn't solve our succinct-proof problem. \(\square\)

HW1 · Problem 4(c)

Short commitment and short opening

Give a \(\lambda\)-bit commitment with an opening of \(O(\lambda\log M)\) bits. Prove position binding.

Show the solution

Use the Merkle tree from the previous lesson. The root is the \(\lambda\)-bit commitment. An opening gives the chosen message and one \(\lambda\)-bit sibling hash at each of the \(\log_2 M\) levels.

The verifier hashes upward to reconstruct the root. If two different messages at the same position reconstructed the same root, somewhere on the two paths different inputs would yield the same hash. This would break collision resistance.

So both size requirements and position binding hold. The tree combines the useful features of parts (a) and (b). \(\square\)

I · Why SNARGs exist · HW3, Problem 4(a)

Put the PCP theorem and Merkle tree together

We now have exactly what we needed: a proof that can be checked by reading a few bits, and a way to authenticate those bits without sending the full proof. Does combining them actually give us cheap and reliable verification?

The PCP theorem supplies the test. The Merkle root makes all answers refer to one fixed proof string. Neither works alone: the PCP box was imaginary, while Merkle authentication tells us that a bit is unchanged, not that the whole statement is true. We need both.

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. A PCP test queries a constant \(k\) positions, chosen before seeing their answers, with perfect completeness and soundness error \(1/2\). Merkle commitments have \(\lambda\)-bit roots and openings of \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and communication polynomial in \(\lambda\) and \(\log n\).

Read the quantities before solving: \(n\) is the public statement length; \(M\) is the number of bits in the encoded PCP proof; “\(\operatorname{poly}(n)\)” means bounded by a fixed power of \(n\). In this problem \(k\) is the fixed number of positions read per PCP test (three in our lecture's version), not the number of address digits called \(k\) in the earlier logarithm example. Here \(\lambda\) is used as both the security parameter and the number of repetitions needed to drive the error down.

Work through the construction and proof

First, the protocol

The prover computes its PCP proof string \(\pi\), builds a Merkle tree over the bits, and sends the root \(c\). This is message one. The root must be sent before the verifier chooses positions, or the prover could change the proof to suit the test.

The verifier chooses fresh randomness for \(\lambda\) independent PCP tests and sends all \(k\lambda\) requested positions together. That's message two. The prover returns the corresponding bits and their Merkle paths in message three.

The verifier checks both that every bit authenticates to root \(c\) and that every PCP test accepts. An authenticated bit is not necessarily a correct proof bit; the PCP predicates are still needed.

Prover \(P\)
⟶
Verifier \(V\)
Send root \(c\)
⟶
Store the fixed commitment
Retain the proof and tree
⟵
Send all test positions
Return bits + Merkle paths
⟶
Check paths and PCP tests

Does an honest proof pass?

Yes. A true statement has a PCP proof that passes every test. Every honest Merkle path also reconstructs the root. Thus the combined protocol has perfect completeness.

Can a false statement pass?

Assume the statement is false. After sending \(c\), a computationally bounded prover cannot change any authenticated bit except by breaking Merkle binding. So, apart from a negligible cryptographic failure, the verifier is testing one fixed PCP string.

For that fixed false proof, the PCP theorem bounds each independent test's acceptance by \(1/2\). All \(\lambda\) tests pass with probability at most \(2^{-\lambda}\). Adding the chance of breaking the Merkle commitment gives

\[\Pr[\text{false acceptance}]\le2^{-\lambda}+\operatorname{negl}(\lambda).\]

Here \(\operatorname{negl}(\lambda)\) denotes a probability that becomes smaller than the reciprocal of any fixed polynomial in \(\lambda\), for large enough \(\lambda\).

Have we kept communication short?

We send one root of \(\lambda\) bits. We authenticate \(k\lambda\) proof positions. Since \(k\) is constant and each path has \(O(\lambda\log M)\) bits, all paths together cost

\[O(k\lambda\cdot\lambda\log M)=O(\lambda^2\log M).\]

Why can we replace \(\log M\) by \(O(\log n)\)? The PCP theorem gives a polynomial bound on \(M\). If \(M\le n^a\) for some fixed constant \(a\), taking logarithms gives \(\log M\le\log(n^a)=a\log n\). That is exactly what \(O(\log n)\) means. The query indices and opened bits don't change the leading asymptotic bound, so total communication is \(O(\lambda^2\log n)\).

We have now proved the two things the question asked: negligible soundness error and succinct communication. Merkle binding makes the PCP tests apply to one fixed proof; the PCP theorem makes those few tests meaningful. \(\square\)

We have our first real construction: a succinct interactive argument. It has short communication and small soundness error. But the verifier still sends random queries, so it isn't non-interactive yet. We'll remove that message later with Fiat–Shamir.

Now notice something else. This construction checks an encoded proof bit by bit. For PLONK we want a different approach: put computation values into a polynomial and test algebraic equations about them. We already understand the principle of a fixed oracle; let's change what the oracle stores and what the verifier may ask it.

Lecture §2.1 · Interactive Oracle Proofs

Why did we use an imaginary box first?

We've seen the same construction in two stages. First the PCP theorem told us that a few correctly selected bits can test a fixed encoded proof. Then a commitment scheme forced the real prover to supply bits from one fixed encoding. This separation is not peculiar to PCPs: it's the blueprint behind modern SNARG constructions.

In the first stage, we pretend there is a trusted oracle, or proof box, storing one object supplied by the prover. It allows the verifier to ask only specific kinds of queries. We prove completeness and soundness in that ideal model, without cryptographic assumptions. This is called an Interactive Oracle Proof (IOP).

In the second stage, a cryptographic commitment replaces the oracle. The prover must commit to the object before seeing the verifier's query, and authentication stops it from changing answers later. After that, Fiat–Shamir can often remove the verifier's interactive challenge. We won't yet assume that this last step is automatically secure; we'll return to its conditions.

Why might we want a different kind of box?

The PCP box stores bits and answers “what is the bit at position \(i\)?” But a long computation consists of numbers that satisfy equations. Perhaps it would be more natural if the box could answer questions about those numbers or equations directly.

The lecture describes three interfaces. We already know the first one:

IOP typeWhat the prover fixesWhat the verifier can ask
PCPA string \(\pi\) of bits.“What is bit \(i\)?” The oracle reveals \(\pi_i\).
Linear IOPA list \(\boldsymbol\pi=(\pi_1,\ldots,\pi_n)\) of field values.“Calculate the weighted sum \(\sum_i q_i\pi_i\),” where the verifier chooses weights \(q_i\).
Polynomial IOPA polynomial \(f(X)\) over a field.“What is \(f(z)\)?” The verifier chooses the point \(z\).

A linear combination is just a weighted sum: with values \((2,3,4)\) and weights \((1,0,2)\), the answer is \(1\cdot2+0\cdot3+2\cdot4=10\). A polynomial evaluation is just substitution: if \(f(X)=X^2+1\), asking at \(z=3\) gives \(f(3)=10\).

These interfaces all describe which questions are allowed. They do not themselves prove that an oracle-based protocol is sound. We still have to construct a meaningful verifier test and prove its security.

This explains the next part of the lecture. The PCP route gave us a conceptually simple but inefficient SNARG construction. For PLONK, we'll use a polynomial IOP instead. Why polynomials? Because they let us represent the results of a long computation and express many required equations as a small number of polynomial identities. We'll see exactly how using Fibonacci, then prove why testing those identities at random points works.
