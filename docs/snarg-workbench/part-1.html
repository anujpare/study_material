Lecture §1 · Why SNARGs exist

How can we trust a long computation without repeating it?

Suppose a server applies SHA-256 to an input one million times and returns the final hash. You want to know whether the answer is correct, but recomputing the million steps yourself defeats the reason for using the server. The lecture asks whether the server can give a convincing proof that is much cheaper to check.

What evidence would convince us in the ordinary way?

The server could send every intermediate hash. The verifier would check the first hash against the starting input, check each subsequent transition, and check that the final hash equals the claimed result. If every transition is correct, the claimed result is correct.

But this method requires almost a million checks and a million transmitted values. It proves the claim without saving the verifier much work. Sending only the final hash is cheap, but then the verifier has no reason to trust it. We need a different kind of proof.

Separate the public claim from its witness

Call the public statement \(x\). In this example it contains the starting input, the number of SHA-256 applications, and the claimed final hash. Call the long list of intermediate hashes \(w\), the witness. A deterministic checking algorithm \(R\) takes \(x,w\) and returns 1 exactly when the witness correctly establishes the claim.

The set of statements for which some valid witness exists is called a language:

\[L=\{x:\exists\,w,\ R(x,w)=1\}.\]

The symbol \(\exists\) means “there exists.” An NP language is one for which a YES statement has a witness of polynomially bounded length that a deterministic algorithm can verify in polynomial time. We need that definition because the later PCP theorem applies to all NP statements.

Call the party who knows the witness the prover \(P\), and the party checking the claim the verifier \(V\). We hope the prover can send a different, short proof string \(\pi\), instead of revealing the whole witness \(w\).

What must a trustworthy proof guarantee?

Completeness means an honest prover with a valid witness convinces the verifier of a true statement. The lecture uses perfect completeness: the honest proof is always accepted.

Soundness means a dishonest prover cannot convince the verifier of a false statement except with small probability. The probability may arise from the verifier's random choices. Let \(\varepsilon\) denote the permitted soundness error:

\[ \Pr[\text{accept}\mid\text{honest proof of true }x]=1,\qquad \Pr[\text{accept}\mid x\notin L]\le\varepsilon. \]

These are security requirements, not an algorithm for constructing the proof. We still have to show how a verifier can reject false statements without reading the entire witness.

We have defined the goal: a convincing proof that saves the verifier work. The next lesson makes “saves work” precise. Only then will we ask how such a proof can be constructed.

Lecture §1 · Succinctness and non-interactivity

What exactly must a short proof save?

Sending the entire witness lets the verifier check the computation, but the proof is as long as the computation trace. Sending only the result is cheap, but not convincing. We need a proof that is both trustworthy and inexpensive to verify. The lecture calls the required efficiency succinctness.

There are two separate costs. The prover sends a proof string \(\pi\); its length in bits is \(|\pi|\). The verifier spends time checking that string; call its running time \(T_V\). A proof that is short but takes a million operations to verify does not solve our problem. Nor does a fast check that first requires downloading the entire witness.

How slowly should these costs grow?

Let \(|x|\) be the length of the public statement and \(|w|\) the length of the ordinary witness. Let \(\lambda\) be a security parameter, chosen large enough to make computational attacks unlikely. The lecture's succinctness requirements are

\[ \boxed{ |\pi|=O\bigl(\lambda,\operatorname{polylog}(|x|,|w|)\bigr),\qquad T_V=O\bigl(\lambda,|x|,\operatorname{polylog}(|w|)\bigr). } \]

Here \(\operatorname{polylog}(n)\) means a fixed power of a logarithm, such as \((\log_2 n)^2\). The logarithm grows slowly: \(\log_2(1024)=10\) because ten doublings produce 1024. The \(O\) notation describes how cost grows for large inputs, not the exact number of bytes or milliseconds. The notation with several arguments is the lecture's shorthand for dependence on those quantities.

The verifier may need time proportional to \(|x|\) because it must at least read the public statement. What we want to avoid is work proportional to the entire witness \(w\). Notice that succinctness constrains the verifier, not the prover: the prover may still do the expensive computation.

Why must the proof also be non-interactive?

Imagine a cryptocurrency transaction that thousands of people may need to verify. If each verifier must send fresh questions to the original prover, the proof cannot simply be published and checked later. A non-interactive proof is one string that any verifier can check using the public statement, without a new conversation.

The lecture calls a proof system satisfying these two requirements a SNARG, for Succinct Non-Interactive Argument. “Argument” means soundness is computational: it is guaranteed against efficient adversaries under cryptographic assumptions, rather than against every mathematically possible prover.

Zero knowledge is a different property: it limits what the verifier learns about the witness. The lecture deliberately leaves that property aside while constructing the succinct argument. We should not confuse a short proof with a private proof.

What makes succinctness difficult?

An ordinary NP proof consists of the witness itself. Reading it takes time proportional to its length. We therefore need a verification method that learns enough to detect cheating while examining only a small part of specially prepared evidence.

That raises the first real construction question: could a verifier check just a few positions in a long proof and still reject false claims reliably? We will first try this idea on an ordinary computation trace, see why it fails, and then learn what the PCP theorem changes.

Lecture §2 · The box game and PCP theorem

Could three checks ever convince us?

Our goal is to verify a long computation without checking every step. Could we simply inspect a few randomly chosen steps? First we need to find out whether a false computation could escape such a test.

Suppose the prover gives us all the intermediate results and cheats only at the very last step, replacing the correct final value with a different one. There might be a million transitions to check, with just one inconsistent transition. Three uniformly chosen different transitions would catch that particular lie with probability only about \(3/1{,}000{,}000\). Sending short questions is easy; making those questions reveal an error is the hard part.

So the problem is the representation of the evidence. A false claim can have a trace that agrees with nearly every locally checked step. We need to arrange the proof so that false claims cannot hide behind just a few bad positions.

What if the proof were encoded differently?

Instead of using the original computation trace, we could encode its evidence: construct a new bit string with extra relations that the verifier can test. The question is whether an encoding exists for which a few carefully selected checks detect false claims reliably.

The surprising answer is yes. The PCP theorem—Probabilistically Checkable Proofs—says that for any NP statement there is a specially encoded proof whose correctness can be tested by reading only a constant number of its bits: three in the version used by this lecture.

This is a theorem the course gives us, not something proved by the check-digit analogy. The verifier uses the prescribed randomized PCP test; it does not simply pick any three positions from the ordinary witness. For a true statement, an honest prover can construct an encoded proof that always passes; an arbitrary string need not pass. For a false statement, every fixed proof string passes with probability at most \(1/2\), where the probability comes from the verifier's random choice of test:

\[ \Pr[\text{accept}\mid\text{true statement, honest proof}]=1,\qquad \Pr[\text{accept}\mid\text{false statement}]\le\tfrac12. \]

Call the encoded proof \(\pi_{\mathrm{PCP}}\), and let \(M\) be its length in bits. The theorem lets \(M\) grow polynomially with the size of the statement. It's not claiming that the full encoded proof is short; indeed it may be longer than the original witness. The verifier reads only three proof bits per test. Later, when we turn this ideal test into a real protocol, we will account for the cost of identifying their positions.

One hidden assumption matters enormously

The verifier's guarantees assume it is testing one fixed encoded proof. If we tell a dishonest prover which positions we're about to inspect and let it invent the corresponding answers afterward, we are no longer testing one string. It can supply whatever answers suit those particular questions.

For the moment, imagine a magic proof box. The prover places all of \(\pi_{\mathrm{PCP}}\) inside and locks it before the verifier chooses its questions. The box answers each position query from that same fixed string. We can now apply the PCP theorem honestly.

How do we get a smaller error than \(1/2\)? Run \(t\) independent tests against that same fixed proof, using fresh verifier randomness, and accept only when every test passes. For a false statement the acceptance probability is at most

\[\left(\frac12\right)^t=2^{-t}.\]

We have overcome the first obstacle only inside the imaginary box model: specially encoded evidence lets a verifier read very little while detecting false claims with bounded error.

There is now exactly one obstacle to making this into a real protocol. Sending the entire PCP string to the verifier would defeat succinctness. Asking the prover directly for three bits would let it adapt its answers. We need to fix a long list with one short commitment and later authenticate a few chosen entries. That's the problem solved by a vector commitment.

Lecture §2 · Vector commitments and Merkle trees

How can we replace the imaginary PCP box?

The PCP theorem gives us a randomized test of three bits from one fixed encoded proof. In the ideal model, a proof oracle stores that string and answers queries consistently. A real prover could wait to see the three positions and invent favorable bits. We therefore need a way to fix the complete string before the queries, without sending the string itself.

What must a real replacement provide?

Call the encoded proof \(\pi=(\pi_1,\ldots,\pi_M)\), a list of \(M\) bits. A vector commitment lets the prover produce a short commitment \(c\) to the entire list. Later, when the verifier asks for position \(i\), the prover sends the bit \(\pi_i\) and an opening proof that authenticates this answer against \(c\).

Why isn't simply sending \(\pi_i\) enough? The prover could send 0 or 1 depending on which answer passes the verifier's test. The commitment must be position-binding: once \(c\) is fixed, a computationally bounded prover cannot successfully open the same position to two different values. That is the rule the ideal oracle enforced automatically.

How can one short value commit to a long list?

We need a hash function \(H\), which maps an input string to a fixed-length digest. The security property used here is collision resistance: finding two distinct inputs with the same digest should be computationally infeasible. Let \(\lambda\) be the digest length in bits, chosen to provide the desired security level.

Start by hashing each proof bit, together with its unambiguous leaf encoding. These digests are the leaves of a binary Merkle tree. For each pair of neighboring leaf digests, concatenate their encodings and hash the result to obtain a parent digest. Continue pairing and hashing until one digest remains. That final digest is the Merkle root \(c\).

The root has \(\lambda\) bits regardless of how many leaves the tree contains. It is not a compressed copy from which the verifier can recover the proof. It is a short value against which individual entries can later be authenticated.

How does an opening work?

Suppose the verifier asks for bit \(i\). The prover supplies that bit and the neighboring digest at each level of the tree. The verifier hashes the bit to reconstruct its leaf digest, combines it with the first neighboring digest in the correct left-right order, and continues upward. It accepts the opening only if the reconstructed root equals the previously received \(c\).

Authenticate one queried proof bit

Move the index to change the opening. The root stays fixed. The highlighted authentication path shows which hashes are recomputed and which neighboring hashes must be supplied.

For \(M=2^k\) leaves, the tree has \(k=\log_2M\) levels. One sibling digest is needed at each level, so the opening contains \(k\) digests of \(\lambda\) bits each. Its authentication data therefore has length \(O(\lambda\log M)\). This is the reason the binary tree is useful: authenticating one position does not require transmitting all \(M\) proof bits.

Why does a Merkle root bind each position?

Assume a dishonest prover opens the same position to two different bit values, and both openings reconstruct the same committed root \(c\). Follow the two authentication computations upward from that position.

If the two differently encoded leaf values produce the same leaf digest, the prover has found a collision in \(H\). Otherwise their leaf digests differ. Since both paths end at the same root, there must be a first level at which two different hash inputs produce the same parent digest. That is also a collision.

Thus two conflicting accepted openings would yield a hash collision. Under the collision-resistance assumption, no efficient prover can produce such openings with more than negligible probability.

The Merkle root enforces the fixed-answer property that the PCP theorem requires. This is the cryptographic reason a real prover can replace the ideal proof oracle. \(\square\)

Does Merkle authentication prove the computation is correct?

No. A prover can commit perfectly consistently to an entirely false encoded proof. Merkle authentication establishes only that the returned bits belong to the fixed string. The PCP test is what makes a false claim unlikely to pass. We must apply both checks to the same openings.

I · Why SNARGs exist · HW1, Problem 4

Homework: three ways to commit to a list

We need to fix a long list before the verifier chooses which entry to inspect. A vector commitment does exactly that. This homework compares three ways to construct one and asks why the prover cannot later open the same position to different values.

Let \(H:\{0,1\}^{\ast}\to\{0,1\}^{\lambda}\) be a random oracle. We have \(M\) messages, each of \(|m|\) bits. The symbol \(\{0,1\}^{\ast}\) means any finite bit string.

HW1 · Problem 4(a)

Long commitment, no extra opening proof

Give a commitment of \(M\lambda\) bits whose opening requires \(O(1)\) extra bits. Prove position binding.

Show the solution

Put every message hash directly into the commitment:

\[c=(H(m_1),\ldots,H(m_M)).\]

To open position \(i\), reveal \(m_i\). The verifier hashes it and compares the result with the stored \(i\)-th hash. No additional authentication proof is needed.

Suppose both \(m_i\) and \(m_i'\ne m_i\) pass. They must satisfy \(H(m_i)=c_i=H(m_i')\). That's a collision in \(H\), which a polynomial-time adversary cannot feasibly find in the random-oracle model.

Thus the commitment is position binding. We saved opening size by paying for \(M\) hashes in the commitment. \(\square\)

HW1 · Problem 4(b)

Short commitment, reveal the whole list

Give a commitment of \(\lambda\) bits with an opening of \(O(M|m|)\) bits. Prove position binding.

Show the solution

Hash an unambiguous encoding of the entire ordered list:

\[c=H(\operatorname{Encode}(m_1,\ldots,m_M)).\]

To open index \(i\), send the entire list. The verifier recomputes its hash, checks it equals \(c\), and reads entry \(i\).

Could two different values at position \(i\) both work? Then two different encoded lists would have the same hash \(c\), another collision in \(H\).

The commitment is short and position binding, but each opening reveals the full list. This doesn't solve our succinct-proof problem. \(\square\)

HW1 · Problem 4(c)

Short commitment and short opening

Give a \(\lambda\)-bit commitment with an opening of \(O(\lambda\log M)\) bits. Prove position binding.

Show the solution

Use the Merkle tree from the previous lesson. The root is the \(\lambda\)-bit commitment. An opening gives the chosen message and one \(\lambda\)-bit sibling hash at each of the \(\log_2 M\) levels.

The verifier hashes upward to reconstruct the root. If two different messages at the same position reconstructed the same root, somewhere on the two paths different inputs would yield the same hash. This would break collision resistance.

So both size requirements and position binding hold. The tree combines the useful features of parts (a) and (b). \(\square\)

I · Why SNARGs exist · HW3, Problem 4(a)

Put the PCP theorem and Merkle tree together

We have two ingredients: the PCP theorem supplies a meaningful three-bit test, and a Merkle commitment authenticates the answers against one fixed proof. This homework asks whether combining them really produces a protocol with low soundness error and short communication. We will calculate both rather than assume they follow.

In the ideal PCP model, the verifier's random test is meaningful because all answers come from one fixed proof string. A Merkle commitment can enforce that consistency without transmitting the string. The exercise asks you to combine these two results, then prove that the resulting protocol has both negligible soundness error and short communication.

Try to identify the required message order before opening the solution: the prover must fix the string first, the verifier must choose queries second, and only then may the prover reveal authenticated answers.

HW3 · Problem 4(a) · Original task

A PCP proof for a statement of length \(n\) has \(M=\operatorname{poly}(n)\) bits. A PCP test queries a constant \(k\) positions, chosen before seeing their answers, with perfect completeness and soundness error \(1/2\). Merkle commitments have \(\lambda\)-bit roots and openings of \(O(\lambda\log M)\) bits. Construct a three-message argument with negligible soundness error and communication polynomial in \(\lambda\) and \(\log n\).

Read the quantities before solving: \(n\) is the public statement length; \(M\) is the number of bits in the encoded PCP proof; “\(\operatorname{poly}(n)\)” means bounded by a fixed power of \(n\). In this problem \(k\) is the fixed number of positions read per PCP test (three in our lecture's version). Here \(\lambda\) is used as both the security parameter and the number of repetitions needed to drive the error down.

Work through the construction and proof

1. Construct the three messages

First the prover constructs the encoded PCP proof and sends a Merkle root \(c\) committing to the entire string. Only after receiving \(c\) does the verifier choose its random PCP tests and send their requested positions. Finally the prover returns the bits and Merkle authentication paths. The verifier checks each path against \(c\) and then evaluates the PCP predicates on those authenticated bits.

2. Choose the repetition count

One PCP test has soundness error at most \(1/2\), which is too large. Run \(\lambda\) independent tests against the same committed proof and accept only if all pass. If one test reads \(k\) bits, at most \(k\lambda\) positions must be opened. Repeated positions can share an opening, but counting all of them gives a valid upper bound.

3. Prove completeness

Yes. A true statement has a PCP proof that passes every test. Every honest Merkle path also reconstructs the root. Thus the combined protocol has perfect completeness.

4. Prove soundness

Assume the statement is false. After sending \(c\), a computationally bounded prover cannot change any authenticated bit except by breaking Merkle binding. So, apart from a negligible cryptographic failure, the verifier is testing one fixed PCP string.

For that fixed false proof, the PCP theorem bounds each independent test's acceptance by \(1/2\). All \(\lambda\) tests pass with probability at most \(2^{-\lambda}\). Adding the chance of breaking the Merkle commitment gives

\[\Pr[\text{false acceptance}]\le2^{-\lambda}+\operatorname{negl}(\lambda).\]

Here \(\operatorname{negl}(\lambda)\) denotes a probability that becomes smaller than the reciprocal of any fixed polynomial in \(\lambda\), for large enough \(\lambda\).

5. Bound communication

We send one root of \(\lambda\) bits. We authenticate \(k\lambda\) proof positions. Since \(k\) is constant and each path has \(O(\lambda\log M)\) bits, all paths together cost

\[O(k\lambda\cdot\lambda\log M)=O(\lambda^2\log M).\]

Why can we replace \(\log M\) by \(O(\log n)\)? The PCP theorem gives a polynomial bound on \(M\). If \(M\le n^a\) for some fixed constant \(a\), taking logarithms gives \(\log M\le\log(n^a)=a\log n\). That is exactly what \(O(\log n)\) means. The query indices and opened bits don't change the leading asymptotic bound, so total communication is \(O(\lambda^2\log n)\).

We have now proved the two things the question asked: negligible soundness error and succinct communication. Merkle binding makes the PCP tests apply to one fixed proof; the PCP theorem makes those few tests meaningful. \(\square\)

We have our first real construction: a succinct interactive argument. It has short communication and small soundness error. But the verifier still sends random queries, so it isn't non-interactive yet. We'll remove that message later with Fiat–Shamir.

Now notice something else. This construction checks an encoded proof bit by bit. For PLONK we want a different approach: put computation values into a polynomial and test algebraic equations about them. We already understand the principle of a fixed oracle; let's change what the oracle stores and what the verifier may ask it.

Lecture §2.1 · Interactive Oracle Proofs

Why did we use an imaginary box first?

PCPs and Merkle trees give us one way to check a large computation. But the PCP encoding is expensive. We want to keep the useful part—the verifier asks only a few questions about fixed evidence—while choosing a representation better suited to arithmetic. That leads to interactive oracle proofs and, eventually, polynomial queries.

In the first stage, we pretend there is a trusted oracle, or proof box, storing one object supplied by the prover. It allows the verifier to ask only specific kinds of queries. We prove completeness and soundness in that ideal model, without cryptographic assumptions. This is called an Interactive Oracle Proof (IOP).

In the second stage, a cryptographic commitment replaces the oracle. The prover must commit to the object before seeing the verifier's query, and authentication stops it from changing answers later. After that, Fiat–Shamir can often remove the verifier's interactive challenge. We won't yet assume that this last step is automatically secure; we'll return to its conditions.

The prover's fixed evidence need not be a bit string. For arithmetic computations, we can instead ask an oracle for numerical combinations or polynomial values. The lecture distinguishes these interfaces by the kind of query the verifier may make.

What must change to verify arithmetic efficiently?

The lecture describes three interfaces. We already know the first one:

IOP typeWhat the prover fixesWhat the verifier can ask
PCPA string \(\pi\) of bits.“What is bit \(i\)?” The oracle reveals \(\pi_i\).
Linear IOPA list \(\boldsymbol\pi=(\pi_1,\ldots,\pi_n)\) of field values.“Calculate the weighted sum \(\sum_i q_i\pi_i\),” where the verifier chooses weights \(q_i\).
Polynomial IOPA polynomial \(f(X)\) over a field.“What is \(f(z)\)?” The verifier chooses the point \(z\).

A linear combination is just a weighted sum: with values \((2,3,4)\) and weights \((1,0,2)\), the answer is \(1\cdot2+0\cdot3+2\cdot4=10\). A polynomial evaluation is just substitution: if \(f(X)=X^2+1\), asking at \(z=3\) gives \(f(3)=10\).

These interfaces all describe which questions are allowed. They do not themselves prove that an oracle-based protocol is sound. We still have to construct a meaningful verifier test and prove its security. The lecture briefly introduces linear IOPs because a later lecture uses them for aggregating private statistics; our present goal is the polynomial IOP used by PLONK.

We will now apply the same fixed-evidence, few-query principle to a polynomial representation, starting with a concrete claim from the lecture: the value of the hundredth Fibonacci number. The immediate question will be how the prover can represent a sequence of 101 values in a polynomial. Only then will we ask what field arithmetic or polynomial identities we need to check it.
