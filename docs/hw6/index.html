II · Computing on shares

Does sharing rely on a hard problem?

HW6 1(a.i)

A computational security argument says that an attack requires too much computation. A perfect-privacy argument says that the observed values have exactly the same distribution for every possible secret. No amount of computation separates identical distributions.

The question asks whether every decision problem with efficiently checkable yes-certificates can also be solved efficiently. Here “efficiently” means using a number of steps bounded by a fixed power of the input length. You only need to decide whether the sharing argument assumes that some computation is hard.

I · What MPC protects

Can equality disclose an extra input?

HW6 1(b)

The ideal execution gives each party its own input and the prescribed output. To disprove a claim about every function, one function is enough. A constant function is useful because its output gives no information about the other input.

Interpret “reveals the other input” as an additional, reliable disclosure, so the recipient learns that the disclosed value really is the other input. Simply writing down your own input is not such a disclosure.

Give me a hint

Compare with the worked solution

  1. Push. Party samples fresh , computes , and broadcasts with its authenticated identity and session label. It retains .

  2. Wait. No party reveals an opening until a valid first-stage commitment has been received from every party. Earlier Pull attempts release nothing.

  3. Pull. The sender broadcasts . Recipients check that it opens the previously stored for the same sender and session. They accept only if this check passes; an invalid opening causes abort.

Hiding prevents learning honest messages from their commitments. Binding prevents a sender from replacing its fixed committed message after honest openings become visible. Authenticated broadcast gives all honest parties the same commitments and openings, so they apply the same verification rule.

Scope of this construction. This is the sheet's intended argument against choosing a new message after seeing cleartext. Ordinary hiding and binding alone do not prove the stronger claim that every committed message is independent of other hidden messages: for example, an unprotected commitment could be copied and later opened by copying the original opening. An implementation of that stronger ideal interface must also prevent such copying or related-message attacks, using suitably non-malleable, sender/session-bound commitments or an ideal commitment functionality. “Non-malleable” here means that seeing a commitment does not enable creating a commitment to a related unknown message.

Finally, commit-then-open does not force a malicious sender to provide a valid opening. The protocol may abort; it does not establish general MPC output fairness.
