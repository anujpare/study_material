Part II · How to keep a secret fixed

Lock a secret now, open it later

Suppose the prover is going to be asked a surprise question. We don't want it to change its first answer after learning the question. But we also don't want the verifier to see that answer too early. Can we make something both fixed and hidden?

Make a value fixed now; reveal it later

A commitment does exactly that. To commit to a bit \(b\), the prover chooses random \(r\), calculates \(C=\operatorname{Commit}(b;r)\), and sends only \(C\). Later it reveals \(b,r\), so the verifier can check the opening by recomputing \(C\).

\[C=\mathrm{Commit}(b;r)\]

The bit \(b\) is the secret, \(r\) is the fresh randomness, and \(C\) is the public commitment. The semicolon in \(\operatorname{Commit}(b;r)\) separates the message from the random choice used to hide it.

Hiding

Hiding means the verifier cannot feasibly tell whether \(C\) commits to 0 or 1 before it is opened.

Binding

Binding means the prover cannot open the same commitment as both 0 and 1. Perfect binding means this is impossible even for a prover with unlimited computing power.

These two properties are needed for different reasons. Binding stops the prover changing the graph after the challenge, which protects soundness. Hiding keeps the committed graph secret until an opening, which lets the zero-knowledge simulator work.

From one bit to a graph

A graph can be represented by a matrix \(\boldsymbol B\): the entry \(B_{ij}\) is 1 when there is an edge from vertex \(i\) to \(j\), and 0 otherwise. The prover can commit to every matrix bit separately.

The verifier then knows the graph entries have been fixed, although it cannot yet read them. Later it can ask to open the whole graph or only the edges of a claimed cycle.

But opening the whole original graph might reveal how the secret cycle is arranged. We will first randomly rename its vertices, so revealing the chosen names gives the verifier no privileged map back to the witness.
