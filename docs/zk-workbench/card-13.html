Part V · Repeating a proof

Why sequential simulation is cheaper than parallel

The preceding lesson distinguished sequential from parallel message order. We can now calculate why the simulator's work changes. In a sequential execution, it can finish and, if needed, rewind one session before starting the next. In a parallel execution, the verifier chooses the full challenge vector after all first messages are fixed, so the straightforward simulator must guess the entire vector correctly. One guess of a fair challenge bit succeeds with probability \(1/2\). If we need \(\lambda\) such guesses, we must ask whether we can retry each one separately or whether all must be correct together.

Sequential schedule: finish one repetition before preparing the next

Sequentially: guess the challenge in the first session, rewind that session until it works, and then move to the second. Each session takes two attempts on average. With \(\lambda\) sessions, the expected total is \(2\lambda\) one-session attempts.

\[\mathbb E[\text{single-round attempts in sequence}]=2+2+\cdots+2=2\lambda\]

An unsuccessful guess in session 3 does not require restarting sessions 1 and 2. That's why we add the expected costs rather than multiplying the chance of guessing everything in a single attempt.

Parallel schedule: prepare every commitment before any challenge

In parallel: the straightforward simulator must guess the whole challenge vector \((c_1,\ldots,c_\lambda)\) before sending its first messages. For an honest verifier there are \(2^\lambda\) equally likely challenge vectors. Only one of them matches a particular guess.

\[\Pr[(\hat c_1,\ldots,\hat c_\lambda)=(c_1,\ldots,c_\lambda)]=\left(\tfrac12\right)^\lambda=\frac1{2^\lambda}\]

Thus one full attempt succeeds with probability \(2^{-\lambda}\), and this particular guess-and-rewind method needs \(2^\lambda\) full attempts on average. That grows exponentially with \(\lambda\), instead of linearly.

Why soundness decreases in both schedules

What about soundness? If the public graph has no cycle, each fixed repeated commitment can answer at most one challenge bit. Independent random challenges therefore make all \(\lambda\) tests pass with probability at most \(2^{-\lambda}\), in either message schedule.

Don't claim we have proved that parallel repetition is never zero knowledge. We've only shown that the straightforward simulator from the single protocol becomes inefficient. A different simulator could exist. And a malicious verifier may correlate the challenges, so we cannot simply multiply independent honest-challenge probabilities in a malicious-verifier simulation proof.
