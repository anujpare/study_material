Part IX · Non-interactive zero knowledge

Replace the verifier's random challenge with a hash

A Sigma protocol takes three messages because the verifier must send a fresh unpredictable challenge. Fiat–Shamir removes that message: both parties derive the challenge from the public statement and the prover's first message. The resulting proof consists of one message from the prover.

Compare the two verification rules

Let \(u\) be a Sigma protocol's first message, \(c\) the challenge, \(z\) the response and \(x\) the public statement. In the interactive protocol the verifier samples \(c\) and sends it. Under the Fiat–Shamir transform, the prover computes \(c=H(x,u)\) itself using a hash-like random oracle \(H\).

Change the source of the challenge

Who chooses \(c\), and what is sent?

Switch between the message structures. The verifier's final equation remains the same, but the origin of the challenge changes.

Choose one protocol to see which information is exchanged and how the challenge is generated.
\[\begin{aligned}c&=H(x,u),\\ \pi&=(u,z),\\ V_{\mathrm{NI}}(x,\pi)&=\mathrm{verif}(x,u,H(x,u),z).\end{aligned}\]

The proof \(\pi\) contains the commitment \(u\) and response \(z\), but not a separately transmitted challenge. The verifier recomputes that challenge with the same public \(x\) and \(u\).

Prove completeness

Why an honest proof is accepted

The honest prover runs the Sigma protocol's first step to obtain \(u\), computes \(c=H(x,u)\), then computes the honest response \(z\) for that challenge. The verifier derives the identical \(c\) from \((x,u)\). Since the underlying Sigma protocol has perfect completeness, \(\mathrm{verif}(x,u,c,z)=1\). Therefore the transformed honest proof verifies.

Where does zero knowledge come from if the simulator cannot know \(c\) in advance?

Fiat–Shamir's security arguments use the random-oracle model. In this idealized model, \(H\) behaves like a uniformly random function that is consistently evaluated on repeated inputs. The simulator gets one extra proof-only ability: it may program the oracle's answer at a selected input.

Informal zero-knowledge simulator

Choose a random challenge \(c\). Invoke the underlying Sigma protocol's honest-verifier simulator on \((x,c)\) to obtain \((u,c,z)\). Program the oracle so that \(H(x,u)=c\). Output the proof \(\pi=(u,z)\). The verifier then recomputes \(c\) and checks the accepting transcript, although the simulator never knew the witness.

Why programming also helps extraction

For a proof of knowledge, the extractor can run a prover to the moment it queries \(H(x,u)\), answer with \(c\), obtain \(z\), and then rewind to that query and answer with a different \(c'\). If the prover produces two accepting responses for the same \(u\), the underlying Sigma special-soundness extractor recovers a witness. A full proof must carefully handle how and when the malicious prover queries the oracle; this is the idea, not a complete forking-lemma proof.

Why the model assumption matters

A real hash function is a fixed algorithm, not a truly programmable random oracle. Replacing \(H\) by a concrete hash, as implementations do, is a heuristic justified by additional assumptions about that hash. The simulator's power to program \(H\) is a proof technique in the idealized model, not an operation an ordinary user can perform on a real verifier.

Why not use an empty non-interactive proof for every language?

For problems in P, the verifier can decide the statement itself, so an empty proof works, as in Homework 2. For general hard NP languages, a plain-model, single-message ZK proof with an efficient witness-free simulator would allow efficient randomized membership testing: run the simulator on \(x\) and check its output. On true instances simulated proofs are accepted with high probability; on false instances soundness limits acceptance. That would put the language in BPP, the class of problems decidable efficiently using randomness with bounded error. Random-oracle programmability changes the simulation model and avoids this simple obstacle.

The central lessons now connect: binding fixes the first claim, a challenge makes cheating risky, simulation establishes privacy, and two accepting challenges can establish knowledge. Fiat–Shamir changes how that challenge is obtained, rather than making those proof obligations disappear.
