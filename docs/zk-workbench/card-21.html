Lecture §5 · The Fiat–Shamir transformation

Replace the verifier's random message with a hash

A Sigma protocol has three messages: the prover fixes a first message \(u\), the verifier sends a uniformly random challenge \(c\), and the prover returns a response \(z\). The verifier uses a deterministic rule \(\mathrm{verif}(x,u,c,z)\) to accept or reject. In such a public-coin protocol, the verifier's message contains only its randomness, so we can try to generate that randomness from the public transcript.

Let \(H\) be a public hash function modeled as a random oracle. The prover first constructs \(u\) without knowing the challenge, then computes \(c=H(\operatorname{Encode}(x,u))\). The function \(\operatorname{Encode}\) unambiguously represents the public statement \(x\) and first message \(u\) as a bit string. The prover computes the usual response \(z\) to this challenge and publishes the pair \(\pi=(u,z)\).

\[ \boxed{\pi=(u,z),\qquad V_{\rm NI}(x,\pi)=\mathrm{verif}\bigl(x,u,H(\operatorname{Encode}(x,u)),z\bigr).} \]

This equation defines the new non-interactive verifier \(V_{\rm NI}\): it recomputes the challenge from \(x,u\) and runs exactly the original Sigma verifier on the reconstructed transcript. The challenge need not be transmitted. The hash must be interpreted in the protocol's intended challenge space, preserving its required distribution.

Why completeness still holds

The honest prover uses the same challenge that the verifier recomputes, then calculates a correct response for it. By perfect completeness of the original Sigma protocol, the reconstructed transcript passes. The transformation therefore preserves honest acceptance. \(\square\)

Hashing removes the verifier's message, but we have not yet proved zero knowledge or knowledge extraction. Those properties require the random-oracle security model, especially the simulator's ability to program a hash answer and the extractor's ability to rewind an oracle query.
